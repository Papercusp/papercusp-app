title: Harness snapshots

A **harness snapshot** is the frozen state of one specific harness at a
moment in time: the project files, the `.papercusp/` directory, the
plugin enablement set with their (redacted) configs, and the database
rows that belong to this harness. Snapshots are how you save your work,
share a working setup with someone else, or roll back a mission to a
known-good point.

Templates are *recipes*. Snapshots are *frozen instances*. You install
a template to start fresh; you instantiate a snapshot to fork an
existing harness's state.

## When to use a snapshot

- **Save mid-mission progress** before a risky change (e.g. switching
  the agent model, replanning, large prompt edits).
- **Share a working harness** with a teammate so they can pick up where
  you left off.
- **Publish an example** to the marketplace that demonstrates a
  finished mission with all its decisions, validations, and outputs
  intact.
- **Hand off** between machines or between operators.

## Lifecycle

Five buttons on the snapshots page (`/snapshots` in the operator UI):

| Button | What it does |
|---|---|
| **save snapshot** | Capture the current harness's state to a `.tar.gz` in `<project>/.papercusp/snapshots/`. Surfaced from the harness toolbar. |
| **Instantiate** | Fork a snapshot into a new project directory. Slug-rewrites the harness name to avoid collision. |
| **Publish** | Upload the tarball to the marketplace under a chosen slug + version. |
| **Retract** | Pull a published version back: `deprecate` (warn), `withdraw` (refuse new installs), or `yank` (specific version only). |
| **Delete** | Remove the local tarball + `.published.json` sidecar. Marketplace copies are unaffected. |

## What's in a snapshot

The capture pipeline tars these by default:

```
<project-root>/
├── .papercusp/                       (everything except logs/, pi-sessions/, screenshots/)
├── source/                         (project source — .git excluded unless --include-git)
└── state/
    ├── db.sql.gz                   (Postgres dump scoped to this harness)
    ├── shared-*.csv                (cross-harness rows that belong to this slug)
    └── harness/proposals/, …       (any reviewer-touched files)
```

It explicitly **excludes**:

- `.env`, `*.pem`, secrets denylist matches (always)
- `.git/` (opt-in via `--include-git`)
- `node_modules/`, `__pycache__/`, `.venv/`, build outputs (re-derivable)
- `pi-sessions/`, `screenshots/`, `pending-reviews/` (per-machine ephemeral)
- `audit_log.csv` (cross-harness, would leak other harnesses)

## Plugin configs are redacted

When the snapshot captures plugin configs, every field declared with
`ui:widget: "password"` in the plugin's `uiSchema` is replaced with
`[REDACTED]`. So Cloudflare tokens, GitHub PATs, Slack webhook URLs,
and similar never ship. The recipient enters their own when they
instantiate.

If you need to ship a plugin secret along with the snapshot (rare —
this is usually a smell), use a CI/CD secret store and inject it
post-install rather than capturing it.

## Authoring workflow

```bash
# 1. Save locally from the operator UI ("save snapshot" in the toolbar).
#    Or via the CLI:
papercusp snapshot publish <harness-slug> --name "milestone-1"

# 2. Test the round-trip — instantiate into a scratch project, verify
#    everything still works.
papercusp snapshot fork @you/my-snapshot --as scratch-test

# 3. Publish to the marketplace.
papercusp snapshot publish-id <snapshot-id> --slug @you/my-snapshot --version 1.0.0
```

The operator UI does steps 1 and 3 with one click each; the CLI is
useful for scripted captures (e.g., a cron job that snapshots a
long-running harness daily).

## Submitting to the marketplace

Snapshots publish to the same marketplace as templates and plugins.
First publish under `@your-handle/...` triggers GitHub-OAuth, the same
flow described in the [Templates page](/docs/harness-templates#submitting-to-the-marketplace).

After publish:

- Listed under [Snapshots](https://papercuspai.com/marketplace?kind=snapshot).
- Anyone can `papercusp snapshot fork @you/my-snapshot` to instantiate
  their own copy.
- Detail page shows the harness lineage, plugin set, and capture metadata.

## Retract / unpublish

If you need to pull a published snapshot — say it accidentally
contained data it shouldn't — three escalating options:

| Action | Effect |
|---|---|
| `deprecate` | Stays installable; warns on `papercusp install`. |
| `withdraw` | Refuses new installs. Existing installs keep working. |
| `yank` | Removes a specific version from the marketplace entirely. |

Run from the operator UI's snapshot page (the **Retract** button) or
the CLI:

```bash
papercusp retract @you/my-snapshot --action yank --version 1.0.0-ts1234567 \
  --reason "leaked test data; rotated key; please use 1.0.1"
```

## Tips

- **Name snapshots meaningfully**. Default names are timestamps; a
  human-readable name like `milestone-1-passing` saves you confusion
  later.
- **Use the description field**. It surfaces in the marketplace listing
  and on the snapshot's detail page.
- **Before publishing**, run a `papercusp doctor --snapshot <id>` to
  re-check redactions; the redaction pipeline runs at capture time but
  it's cheap to verify before broadcasting.
- **One snapshot per state, not per timestamp**. If you snapshot daily,
  use `papercusp snapshot delete` to prune old ones — they're cheap on
  disk but accumulate.
