A **plugin** extends what every harness can do: it adds dashboard tabs,
toolbar actions, lifecycle hooks, scheduled routines, and database
schemas. Plugins ship as standalone packages on the marketplace and
install per-machine, then enable per-harness.

The reference plugins that ship with Papercusp —
`@papercupai/cloudflare-pages`, `@papercupai/slack-notifier`,
`@papercupai/jira-sync`, `@papercupai/notion-export` — are themselves
just plugins published to the marketplace.

## What a plugin can contribute

Plugins declare contributions in their manifest:

| Surface | What it is | Example |
|---|---|---|
| **dashboardTabs** | A tab that appears in the harness dashboard | docs-viewer adds a "Docs" iframe tab |
| **sidebarItems** | A link in the operator's left sidebar | Linear plugin adds "Linear" |
| **harness-toolbar actions** | A button next to "save snapshot" / "start" | cloudflare-pages adds "Publish website" |
| **lifecycle hooks** | Code that runs on `mission.start`, `onFeaturePassed`, etc. | slack-notifier posts a message on `mission.done` |
| **routines** | Scheduled triggers (cron / webhook / API) | briefings runs daily at 9am |
| **api routes** | Plugin-owned HTTP endpoints under `/api/plugins/<name>/` | postgres-manager exposes `/migrations/run` |
| **schemas** | Postgres DDL the plugin owns (run at install time) | jira-sync owns `plugin_jira.issues` |

Each of these is opt-in via a capability declaration. A plugin that
wants to read secrets must list `secrets:read:<NAME>` (or
`secrets:read:PREFIX_*`). A plugin that wants to fetch a URL must list
`http:fetch:<host>` (or `http:fetch:*.subdomain`). The runtime refuses
to load plugins whose declared capabilities don't cover what the code
actually does, and refuses to invoke handlers whose capabilities aren't
satisfied.

## Anatomy of a plugin

```
my-plugin/
├── papercusp.json       # manifest: name, capabilities, dashboardTabs, actions, routines, …
├── index.ts             # default-exports a Plugin (init/onLoad/hooks/routines)
├── dist/index.cjs       # compiled CJS — the loader prefers this over .ts
├── tab.tsx              # React component for any dashboardTab (optional)
├── README.md
└── (optional) sql/init.sql   # plugin schema migrations
```

The minimum manifest:

```json
{
  "name": "@you/my-plugin",
  "version": "0.1.0",
  "kind": "plugin",
  "papercusp": "^0.1.0",
  "description": "What this plugin does.",
  "capabilities": ["events:listen:mission-done", "http:fetch:hooks.example.com"],
  "actions": [
    { "name": "notify",
      "label": "Notify",
      "surfaces": ["mission-done", "harness-toolbar"],
      "capabilities": ["http:fetch:hooks.example.com"] }
  ]
}
```

Action capabilities must be a *subset* of the plugin's top-level
capabilities. The host enforces this at registry-build time — a plugin
can't grant its actions more power than the user consented to at
install.

## Lifecycle hooks

The host fires named hooks at well-known points. Subscribe in
`hooks: { ... }` on the exported Plugin object:

| Hook | When it fires | Receives |
|---|---|---|
| `onLoad(ctx)` / `onUnload(ctx)` | Plugin (un)loaded by the host | ctx |
| `beforeMissionStart(ctx)` | Once before the harness loop starts | ctx |
| `afterDone(ctx)` | After the orchestrator decides DONE | ctx |
| `onPostOrchestrator(ctx, decision)` | After every orchestrator invoke | ctx, decision verb |
| `onPostWorker(ctx, featureId)` | After every worker invoke | ctx, featureId |
| `onPostValidator(ctx, featureId, status)` | After every validator | ctx, featureId, 'passed' \| 'failing' |
| `onFeaturePassed(ctx, featureId)` | When a feature transitions to passed | ctx, featureId |
| `onProposalAccepted(ctx, proposalPath)` | When a SPEC proposal is applied | ctx, proposalPath |

`ctx` carries the install slug, project paths, a logger, the plugin's
private storage path, the action registry, and a capability-gated
`spawn` for invoking subprocess binaries.

## Authoring workflow

```bash
# 1. Scaffold from a reference plugin.
papercusp plugin scaffold @you/my-plugin --from slack-notifier

# 2. Edit. Add actions in the manifest, implement them in init().
#    Build:
cd my-plugin/
npx esbuild index.ts --bundle --platform=node --format=cjs --target=node20 \
  --external:@papercusp/plugin-sdk \
  --footer:js='module.exports = index_default; module.exports.default = index_default;' \
  --outfile=index.cjs

# 3. Iterate locally — symlink the plugin into ~/.papercusp/global-plugins/
#    and enable it on a test harness.
ln -s "$PWD" ~/.papercusp/global-plugins/@you/my-plugin
papercusp plugin enable @you/my-plugin --harness test-harness

# 4. Validate.
papercusp plugin validate

# 5. Publish.
papercusp publish
```

Hot-reload the operator runtime while developing:

```bash
PAPERCUSP_DEV_PLUGIN_WATCH=1 npm run dev:operator
```

This watches `~/.papercusp/global-plugins/` and resets the host cache
on every manifest or entry-file change. The next request rediscovers.

## Capabilities reference

```
events:listen:<event-name>      # subscribe to a host event
events:emit:<event-name>        # fire a custom event
http:fetch:<host>               # exact OR `*.subdomain`
secrets:read:<NAME>             # exact OR `<PREFIX>_*`
storage:plugin-private          # ~/.papercusp/plugin-data/<name>/
db:plugin-schema                # owned Postgres schema (declare in schema field)
compute:exec:<basename>         # spawn a subprocess (basename only — no /paths)
ui:dashboard-tab                # contribute a dashboard tab
ui:sidebar-item                 # contribute a sidebar link
ui:harness-toolbar              # contribute a toolbar button
ui:harness-route                # owns the full /harness/<slug> page
roles:register:<role-name>      # add a custom role to the harness
routines:read|write             # read/write the routine table
tasks:read|write                # ditto for features (legacy: tasks)
goals:read|write
comments:read|write
```

Wildcards: `http:fetch:*.foo.com` matches subdomains;
`secrets:read:YT_*` matches any secret name starting with `YT_`;
`compute:exec:*` is rejected (degenerate).

## Submitting to the marketplace

Same flow as templates and snapshots: GitHub-OAuth on first publish
under `@your-handle/...`, then `papercusp publish` from the plugin
directory. After publish:

- Listed under [Plugins](https://papercuspai.com/marketplace?kind=plugin).
- Operators install via the UI's "Install" button or
  `papercusp install @you/my-plugin`.
- Per-harness enablement happens in the marketplace's "Enable in
  harness…" picker.

## Tips

- **Compile to `index.cjs`**, not `index.js`. If your `package.json`
  declares `"type": "module"`, a `.js` file is treated as ESM and
  CommonJS `module.exports` won't bind. The loader looks for `.cjs`
  first for exactly this reason.
- **Don't import `@papercusp/plugin-sdk` types into bundles** — mark it
  `--external` in esbuild. The host provides the types at runtime.
- **Declare every capability your code uses**. The runtime refuses to
  fire any handler whose capabilities aren't a subset of the plugin's
  declared set. A `compute:exec:ffmpeg` call will throw if you forgot
  to list it.
- **`ui:widget: "password"` in your `uiSchema`** marks a config field
  as sensitive. Snapshots redact those fields automatically. Use it
  for any token, key, or secret your plugin reads.
