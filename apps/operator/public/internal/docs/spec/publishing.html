16. Publishing — hosted Cloudflare publishing (v3)

Status: hosted Worker built; live plugin is BYO-direct-upload

Publishing — one-click public publishing from coding harnesses. The hosted publish Worker (apps/papercusp-publish/) and its shared auth lib (libs/papercusp-publish-auth/) are built and largely match the data-model/endpoint shapes below. Live deployment waits on wrangler d1/kv create + secret put + deploy and a wildcard cert on *.preview.papercuspai.com.

The hosted-publish substrate plugin originally specced here (@papercupai/cloudflare-pages-hosted) was deleted — it shipped with no manifest (revive-plugin-system-2026-06-04 D-005). The surviving plugin is @papercupai/cloudflare-pages, a BYO-Cloudflare direct-upload plugin: it talks to api.cloudflare.com directly with the user’s own token and never contacts publish.papercuspai.com. The hosted Worker and the live plugin are therefore two separate code paths; §§15.2–15.8 below describe the hosted Worker, and the BYO-direct-upload plugin is noted inline where the two diverge.

Three rounds of architectural review have been incorporated (v1 → v2 → v3). Once a real user publishes their first project this page folds into §7 (Plugin extension points) and §11 (Distribution).

15.0 Why this exists

Section titled “15.0 Why this exists”

A non-technical user runs a coding harness, describes what they want in plain English, watches the harness build it, and clicks Publish. Within ~30 seconds they get a public URL they can share. They never touch a Cloudflare credential, never create an API token, never pre-create a project.

Without this, “ship the app” is a half-day of Cloudflare onboarding for the user — a step where the AI-built-an-app value proposition crashes into “log into Cloudflare, generate a Pages:Edit token with these exact permissions, copy your account UUID from the right sidebar…” and the user gives up.

The mechanism is a hosted publish service we run, fronting our own Cloudflare account. Users borrow our infra; we hold the master token; the content’s served on a vanity subdomain we control.

15.1 Goals + non-goals

Section titled “15.1 Goals + non-goals”

Goals

  • One click from harness header → live public URL within ~30 seconds.
  • Zero credentials handled by the user, ever.
  • Coding harness only — papercup-org parents and other non-coding templates do not get a Publish button.
  • Bounded blast radius if our master Cloudflare account is suspended: every user can recover their projects without our infra.

Non-goals (v1)

  • Custom user-owned domains. v1 deploys to *.preview.papercuspai.com.
  • Private/access-gated deployments. v1 is fully public; private mode is spec’d here but built later.
  • Build pipelines. v1 publishes static files from <project>/<exportDir>; the harness already produced the output.
  • Paid-tier billing. Schema supports tenants.tier from day one; enforcement of paid limits comes later.

(The previous location, ~/.papercusp/publish-credentials.json mode 0600, is deprecated.) On the Worker side the tenantSecret is stored directly in tenants.secret_b64 (base64url, cleartext, relying on D1 at-rest encryption), not hashed — the JWT is HMAC-signed with a key derived from the secret, which a one-way HMAC-pepper hash couldn’t verify. (An HMAC-pepper helper exists in the auth lib but is unused by the Worker; v1.1 hardening adds an AES-GCM envelope keyed by HASH_PEPPER.)

Per-publish JWT

Section titled “Per-publish JWT”

The signing key is not the raw tenantSecret: it is an HKDF-SHA256 subkey, publishKey = HKDF(tenantSecret, info="papercusp-publish-v1"). The same secret derives a separate snapshotKey (info="papercusp-snapshot-v1"), and the required aud claim is checked on verify — so a publish token can’t be replayed against snapshot endpoints, and vice versa (see §15.4 HKDF subkeys below).

Worker validation order:

  1. Parse the JWT, look up the tenant by sub, reject if missing or status !== 'active'. Derive publishKey = derivePublishKey(secret_b64) and verify the HMAC signature against it.
  2. Reject if now > exp, now < iat - 5s (clock skew tolerance), or aud !== <expected audience>.
  3. INSERT INTO jti_used (jti, exp) VALUES (?, ?) — duplicate primary key throws → 401. D1 PRIMARY KEY constraint is the atomic replay guard, not KV put.
  4. On /publish/start, recompute canonical manifest sha256 from the request body; reject if !== claims.sha256.

HKDF subkeys + aud scoping

Section titled “HKDF subkeys + aud scoping”

The shared auth lib derives a per-feature subkey from the one tenantSecret via HKDF-SHA256 (RFC 5869, empty salt — the secret is already high-entropy):

Each JWT carries an aud claim ("publish" or "snapshot"); verify rejects on mismatch. A publish token therefore can’t be replayed against snapshot endpoints even though both keys descend from the same secret — the subkeys are domain-separated and the audience is bound into the signed claims.

Canonical manifest (RFC 8785 / JCS)

Section titled “Canonical manifest (RFC 8785 / JCS)”

Substrate and Worker both run the same JCS library. Files pre-sorted by NFC-normalized path; numbers in canonical form; no whitespace. Without this, path-encoding mismatches (NFC vs NFD on macOS, key-order differences across JSON serializers) silently break JWT signature validation and burn debug hours.

Tenant lifecycle

Section titled “Tenant lifecycle”
  • Rotate: POST /rotate-secret with old secret → returns new secret. Old secret invalidated immediately (secret_b64 updated atomically; rotated_from records the previous tenant id for audit).
  • Revoke: admin sets tenants.status = 'revoked'; every subsequent publish returns 401. User must re-register from a fresh substrate install.
  • Last-used audit: every successful publish updates last_used_at + last_ip. Surfaces “this tenant published from a new IP” via the Settings UI for the operator to notice.

15.5 Rate-limit tiers (final ordering)

Section titled “15.5 Rate-limit tiers (final ordering)”
  1. Per-tenant daily — 50/day free, 500/day paid. KV ratelimit:daily:<tid>.
  2. Per-tenant burst — 5/min. KV ratelimit:burst:<tid>.
  3. Per-IP publish-daily — 50/day, independent of tenant. KV ratelimit:ip-publish-daily:<ip>. Closes the wipe-~/.papercusp and re-register loophole that per-IP-on-registration alone doesn’t.
  4. Per-IP register-hourly — 10/hour on /register-tenant. KV ratelimit:ip-register-hourly:<ip>.
  5. Per-file size cap — 25 MB (CF Pages hard limit per file).
  6. Per-deployment file count cap — 20,000 (CF hard limit).
  7. Per-deployment total size cap — 1 GB (our policy; CF doesn’t enforce — saves us bandwidth abuse).

  • Returns: { tenantId, tenantSecret }. Substrate persists both in Postgres (harness_shared.operator_publish_credentials, migration 022).

POST /publish/start

Section titled “POST /publish/start”
  • Auth: JWT.
  • Body: canonical manifest (see §15.4).
  • Returns:
  • Idempotency: re-POSTing the same manifest with the same JWT-sha256 within 30 minutes returns the same deploymentId with missing[] filtered to still-not-uploaded files. Resumable uploads.

PUT /publish/file/<deploymentId>/<sha256>?token=<signedUrlToken>

Section titled “PUT /publish/file/<deploymentId>/<sha256>?token=<signedUrlToken>”
  • Auth: signed-URL HMAC token. The token signs the colon-joined string deploymentId + ":" + sha256 + ":" + exp with JWT_SECRET, and the wire format is b64u(sig) + "." + exp.toString(36) (the exp suffix is appended outside the HMAC and re-folded into the input on verify). The per-file sha256 is a path segment, not a query param.
  • Body: raw file bytes.
  • Worker behavior: buffers the entire body into memory (≤25 MB per §15.5 cap, well under the Worker’s 128 MB limit) so it can verify sha256(body) === <path sha256> before forwarding; rejects on mismatch. It then fans out the buffered bytes in parallel: streams them to CF /pages/projects/<n>/file using the master token, and writes the same bytes to the R2 archive as files/<sha256>.bin. This is not a zero-buffer proxy.
  • Workers Paid prerequisite: $5/mo plan provides 1,000 subrequests per Worker invocation, vs 50 on Free. Required for ≥40-file deployments.

POST /publish/finalize

Section titled “POST /publish/finalize”
  • Auth: JWT.
  • Body: { deploymentId }.
  • Worker behavior:
    1. Verify every deployment_files row is uploaded=1 (else 409 with missingCount). The per-file .bin blobs were already written to R2 during each PUT (§15.6 PUT route), so finalize doesn’t re-upload content.
    2. Call CF /pages/projects/<name>/deployments to publish.
    3. Update the existing deployments row to status='building', cf_deployment_id=<...>, archive_path=<...>. (The row was inserted earlier at /publish/start with status='uploading' and a null cf_deployment_id.)
    4. Fire-and-forget (waitUntil) write of manifest.json to the R2 archive — only the manifest, since the .bin files already landed at PUT time.
    5. Return { vanityUrl, status: 'building' }.

Section titled “GET /publish/status/<deploymentId>”
  • Auth: JWT.
  • Returns: { status: 'building' | 'live' | 'failed', vanityUrl, failureReason? }.
  • Substrate polling: 1s for first 10s, 5s thereafter, total cap 5 min, jittered ±20%.

POST /rotate-secret

Section titled “POST /rotate-secret”

  • Returns: { tenantSecret: <new> }. Old secret invalidated atomic with new secret install (UPDATE in single transaction).

DELETE /publish/<harness> (v1.1)

  • Effect: removes the deployment, frees the project, GCs R2 archive. Plugin gets an Unpublish row in config→Plugins.

POST /admin/gc/* (cron, internal)

Section titled “POST /admin/gc/* (cron, internal)”

The daily cron (scheduled(), 06:00 UTC) POSTs three separate internal endpoints — there is no single GET /admin/gc:

  • POST /admin/gc/abandoned-uploads — deployments stuck in status='uploading' for > 1h are marked status='failed' (failure_reason='abandoned (gc)'). The row is not deleted and no CF DELETE is issued — CF auto-expires its own upload tokens.
  • POST /admin/gc/expired-archives — for deployments past their retention TTL (30d free / 1y paid), deletes the R2 prefix and nulls deployments.archive_path.
  • POST /admin/gc/jti — deletes jti_used rows whose exp has passed.

15.7 BYO-Cloudflare + eject-to-own-CF

Section titled “15.7 BYO-Cloudflare + eject-to-own-CF”

The fire exit. As built, the live @papercupai/cloudflare-pages plugin is BYO-only — it is the eject path. It always calls CF Pages directly with the user’s own token and never contacts publish.papercuspai.com. (The hosted-default mode lives only in the apps/papercusp-publish Worker; the deleted -hosted plugin would have been its client.)

Plugin config schema (live manifest)

Section titled “Plugin config schema (live manifest)”

accountId and projectName are required; exportDir defaults to "out" and branch to "main". The token is read from ~/.papercusp/secrets/CLOUDFLARE_API_TOKEN (or the env var) under the secrets:read:CLOUDFLARE_API_TOKEN capability. The plugin runs the CF Direct Upload flow: GET upload-token → POST assets/check-missing → POST assets/upload (BLAKE3 content-addressed, with SHA-256 fallback) → POST deployments.

Beyond the explicit publish action (with a dryRun param that reports what would deploy without uploading), the plugin auto-publishes on mission completion via an afterDone hook — silently skipping when accountId/projectName aren’t configured, and logging (never failing the mission) on a real CF error.

Eject migration script (unbuilt — design only)

Section titled “Eject migration script (unbuilt — design only)”

The admin-runnable eject migration (apps/papercusp-publish/scripts/eject.ts) is not yet built — apps/papercusp-publish/scripts/ currently holds only install-secrets.sh and smoke-test.mjs. The data-model groundwork exists (R2 archive + deletePrefix), but the migration script itself is future work. Its design, for each tenant’s projects:

  1. Read manifest + per-file content from R2, not CF Pages API. (R2 is the fire exit’s load-bearing component. CF Pages API is unavailable when the master account is suspended; that’s the entire problem.)
  2. Re-upload to user’s BYO CF account using their token.
  3. Rewrite plugin config: set accountId + byoCloudflareToken.
  4. Delete the now-orphaned R2 prefix.

Tertiary fallback: if R2 retention has expired, the substrate’s local <project>/<exportDir> still has the source — re-publish from local. Two independent recovery paths.

Why this matters

Section titled “Why this matters”

WordPress.com → WordPress.org structurally has the same bad-actor blast radius problem in miniature. One user publishing illegal content suspends the master account; every user’s site goes down. The eject path means “every user’s site goes down for ~hours, not forever” — because their site rebuilds from R2 (and worst case: from local source). That’s a tolerable degradation; permanent loss is not.

15.12 What’s NOT in v1

Section titled “15.12 What’s NOT in v1”
  • Multi-master-account sharding. Useful at scale; R2 retention provides a real recovery path, so a single master account is acceptable for v1. Worth revisiting at 1k+ paying users.
  • Machine fingerprinting for tenant binding. Privacy-invasive; per-IP daily cap (§15.5 #3) closes the abuse loop without it.
  • Custom user-owned domains. v1 deploys to *.preview.papercuspai.com only; user-supplied domains in v1.1.
  • Private mode via Cloudflare Access. Schema field projects.access_policy: 'public' | 'private' reserved; Worker enforcement v1.1.
  • Paid-tier billing. tenants.tier column exists; defer billing until we have users.
