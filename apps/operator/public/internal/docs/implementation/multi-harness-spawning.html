1. Goal

Section titled “1. Goal”

Make harness-spawning and cross-harness coordination first-class capabilities of the standard harness substrate, with auth-bound identity from day one.

Concretely:

  • Any harness whose role config declares allowedActions: [..., "scaffold_harness"] can spawn children.
  • Any marketplace template that declares spawnable: { kind, requires } can be spawned as a child.
  • Children whose parent_slug is set automatically report completion back to their parent — no per-template hook authoring required.
  • Every orchestrator understands it’s running inside Papercusp, can see its parent / children / siblings at a glance, and can pull full state of any other harness on demand via authenticated read APIs.
  • Any harness whose role config grants send_message can message any other harness, with a declared reason recorded in the audit log.
  • Every executeAction call is authenticated against a per-harness shared-secret token; harness identity is derived from the token binding, not from caller-supplied body fields. parent_slug and message from_slug are derived (not trusted), so spoofing is impossible at the protocol level.
  • The papercup-org template is the first template that uses these features, not a special case.

The user-facing demo: drop a directive into the papercup-org parent’s inbox, manually invoke its director, watch it spawn children with full context of the org, watch them run while the parent can intervene mid-mission, watch completion flow back.

2. Scope

Section titled “2. Scope”

Closed-loop manual demo via standard substrate. End-to-end smokes must pass:

  • Smoke A — papercup-org happy path (directive → spawn → first non-trivial file → completion message in parent inbox)
  • Smoke B — generic non-papercup-org harness can also spawn children (proves the feature is substrate, not template-specific)
  • Smoke C — neighbor visibility works (a child’s prompt sees its parent’s status; a parent’s prompt sees its children’s statuses; cross-harness supervisor message arrives in child’s prompt-build)
  • Smoke D — auth model holds: a request without a valid token, with a token bound to harness X claiming to be harness Y, or with a forged callingHarness body field, is rejected with 401/403

Autonomy (routine ticker, coordinator dispatch, auditor cadence) is a separate plan — not included here.

3. Non-goals

Section titled “3. Non-goals”
  • Coordinator dispatch — NEXT_HARNESS parses but doesn’t fire children autonomously.
  • Auditor cadence — file exists, no scheduler invokes it.
  • add_directive_summary — context bounded by prompt-build truncation instead.
  • mark_campaign_published, pause_project, resume_project — useful, not needed for the loop.
  • Briefings plugin — gone, dropped from manifest until source is restored or rebuilt.
  • Many-directive scale, multi-week autonomy, KPI dashboards.
  • Cross-machine spawn (parent on machine A, child on machine B).

Section titled “Step 2 — executeAction with 4 verbs + auth (~3.5d)”

Auth middleware (~0.5d):

  • Reject if no Authorization: Bearer header (401).
  • Look up bearer in harness_shared.token_index; if no match → 401.
  • Set derivedCallingHarness = <slug from match> on request context.
  • If body has callingHarness and it doesn’t match → 403 with clear error.
  • If verb is send_message and body has from and it doesn’t match → 403.
  • If verb is scaffold_harness and body has parent_slug → 400 (validation error).

Three SQL-only verbs (~1d):

  • send_message: validate reason ≥ 10 chars; placeholder-regex match logs warning to executed_actions.reason but proceeds. INSERT into harness_<to_slug>.messages with from_slug = <derivedCallingHarness>. If kind === 'Directive', also append to harness_<to_slug>.supervisor_notes.
  • mark_message_status: UPDATE harness_<derivedCallingHarness>.messages (only your own inbox/outbox is yours to mark) SET status = $2, acknowledged_at = now() WHERE id = $1.
  • spinup_project: opens a PG transaction across all affected schemas; INSERT into harness_shared.projects; for each requested department, recurse-in-process to fire follow-up send_message (kickoff/priority/budget) within the same transaction. Single COMMIT or single ROLLBACK. Returns {subActions: [{actionId, op, ok}, ...]} for diagnostic detail.

scaffold_harness (~1.75d):

  • Validate projectSlug, template, spec, goal.
  • Look up template in the spawnable catalog. If not present or spawnable field absent, reject with validation_error: 'template not spawnable'.
