Why both exist (not a duplicate, not a stale-link mistake)

Section titled “Why both exist (not a duplicate, not a stale-link mistake)”

  • The substrate operator UI is part of every Papercusp install — anyone self-hosting gets it.   • The public marketplace at papercuspai.com is install-free — it just shows the catalog. No login, no install state, no API keys. Anyone evaluating Papercusp lands here first.

The substrate UI and public site share the same data source (api.papercuspai.com) but render different concerns. Not a stale duplicate.

Phase M3 — Tarball signing (Ed25519)

Section titled “Phase M3 — Tarball signing (Ed25519)”

Goal: Detect tampering between publish and install.

Plan:

  1. Generate marketplace’s Ed25519 keypair; private key stored at ~/.papercusp/marketplace-key.pem on the marketplace-api host (mode 0600); public key published at https://api.papercuspai.com/v1/keys/marketplace.pub.
  2. At publish:
    • Compute SHA-256 of the tarball.
    • Sign ${slug}\n${version}\n${sha256}\n${published_by}\n${published_at} with the marketplace key.
    • Store the signature in package_versions.signature.
  3. At install:
    • CLI fetches the marketplace public key (cached locally with TTL of 1 day).
    • Verifies signature against the metadata it received from /catalog/:slug/:version.
    • Independently SHA-256 the downloaded tarball and verify it matches the signed sha256.
  4. Failure modes:
    • Signature invalid → install hard-fails with “tarball tampered or marketplace key changed”.
    • Public key fetched but doesn’t match cached → CLI prompts user to confirm rotation (single line, audit logged).

Estimate: 2 hours. The crypto is tweetnacl-grade primitives.

Operational notes

First-party seed templates (re-publishing)

Section titled “First-party seed templates (re-publishing)”

The bundled templates papercup-coding and papercup-org are first-party — they’re owned by @papercupai, not by whoever happens to run the seed script.

Their canonical source-of-truth lives in the marketplace repo at ../papercusp-registry/seeds/papercupai/<slug>/. They’re published via the same publish pipeline as any user package — no SQL backfill, no special case in the server.

Two auth modes cover this:

Service token (recommended for CI / seed scripts): A static bearer token bound to a publisher login. The marketplace operator issues it via PAPERCUSP_MARKETPLACE_SERVICE_TOKENS env (JSON array of {token, login} entries). Then:

The CLI sends the token as Authorization: Bearer ...; the server matches it against the configured table and stamps publishedBy from the bound login. No OAuth round-trip, no browser, fully scriptable.

OAuth Device Flow (for human publishing as @papercupai): papercusp login then papercusp publish. Requires the @papercupai GitHub account/org to exist and you to be able to authenticate as it.

Don’t insert seed packages directly via SQL or backfill scripts — that bypasses the publish pipeline (signing, indexing, webhook events) and creates orphan-attribution problems. The seeds README at ../papercusp-registry/seeds/README.md documents the policy.
