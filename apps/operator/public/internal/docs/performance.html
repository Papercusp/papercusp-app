Stack note — Next.js has been removed

This page was written when the operator app was a Next.js App Router project, and several rules below were framed around RSC / Server Components / Next-specific tooling. That framework is gone. The operator is now a Vite SPA on TanStack Router (apps/operator-vite, dev server on :3055) fronting a Hono host (apps/operator/bin/hono-host.ts, :3070). There is no next dependency, no RSC, no Server Components, and 'use client' is an inert vestige. The next/* import surface (next/image, next/dynamic, next/link, next/navigation) is satisfied by TanStack-Router-backed shims under apps/operator/lib/router-compat/{dynamic,link,navigation}.tsx. RSC-only advice (“ship zero JS”, “push 'use client' to the leaf”) does not apply to a SPA — read those rules as historical context. The measured perf wins (parallelize fs/PG, request-scoped read caches, virtualize/memoize lists, animate only transform/opacity) still hold; only the named cause “Next.js dev mode” and any Next-specific tool are stale. Every agent must read this page before changing code in this repo. “It works” isn’t the same as “it’s fast.” This page captures (a) practices from apps users consider best-in-class — Linear, Notion, Vercel, Figma, Discord, Stripe — and (b) real anti-patterns we’ve shipped that have caused production slowdowns. The “What not to do” section near the bottom is load-bearing: it lists specific traps with measured impact and the correct alternative. If a pattern in your change matches one of those traps, change the approach before continuing.

Hard rules — must follow

Section titled “Hard rules — must follow”

These are non-negotiable. CI / review will reject violations.

1. (Historical — RSC no longer applies) Keep the JS you ship small

Section titled “1. (Historical — RSC no longer applies) Keep the JS you ship small”

Stale on this stack. This rule assumed Next.js App Router Server Components. The operator is now a Vite SPA on TanStack Router — everything ships to the browser; there are no Server Components and 'use client' is a no-op. The rule below is kept for context and for the parts that still generalize.

The SPA-era takeaway: there is no free server-only tier, so be deliberate about what each route’s chunk pulls in. Code-split heavy, not-immediately-needed pieces (see rule 14 with the dynamic shim), keep route bundles under the per-feature delta target, and don’t hoist a one-route dependency into the shared chunk.

Original (Next-era) guidance, for reference only:

2. Virtualize any scrollable list of more than ~50 items

Section titled “2. Virtualize any scrollable list of more than ~50 items”

Rendering 1000 DOM nodes for a list the user only sees 20 of is wasted work. Use @tanstack/react-virtual (already a dependency). RichGrid already handles this for the feature/issues lists; copy that pattern for any new long list.

Anti-pattern: rendering all rows and relying on overflow: auto to “hide” the off-screen ones. The DOM is still there, paint cost is still there.

3. Memoize list-row components by stable key

Section titled “3. Memoize list-row components by stable key”

Every row in a virtualized list should be React.memo-wrapped with an areEqual that compares the row data identity (not deep equality). The parent shouldn’t re-render the row when something elsewhere in the list changes.

Pair with stable identity in the data layer — on the Zero/WebSocket transport useSyncQuery returns the same object reference for unchanged rows. If you map the data into new objects on every render, memoization is useless.

4. Animate only transform and opacity (and filter sparingly)

Section titled “4. Animate only transform and opacity (and filter sparingly)”

These are GPU-composited; the browser handles them off the main thread. Animating width, height, top, left, padding, margin, font-size, or any size-affecting property forces layout + paint on every frame and torches your frame rate.

If you absolutely need to animate size, use motion’s layout prop, which uses FLIP under the hood (compute the start/end rects, animate the transform between them — not the size).

5. Never animate inside a useEffect that depends on a frequently-changing value

Section titled “5. Never animate inside a useEffect that depends on a frequently-changing value”

Animation effects with unstable deps trigger re-render storms. If you find yourself writing useEffect(() => { setTimeout(...) }, [openCount]), you’re about to fire one timeout per render. Use motion’s declarative API (animate prop) instead.

6. Keep server-only code out of the browser bundle

Section titled “6. Keep server-only code out of the browser bundle”

Reframed for the SPA. The old wording (“'use client' files cannot import server-only code”) was a Next.js RSC boundary rule. 'use client' no longer means anything, and app/api/ is gone — server endpoints live in the Hono host (apps/operator/bin/hono-host.ts + lib/endpoint-route/). The underlying hazard is still real on the SPA.

Everything in the operator-vite client tree gets bundled and shipped to the browser. Don’t import Postgres clients, credential loaders, node:fs, or other host-only modules into a component or a file the client tree reaches — it bloats the bundle and can leak secrets. Keep client/server-only types and functions in separate files and cross the boundary via the Hono API (fetch/useSyncQuery), not a direct import.

7. Don’t add a dependency you’ll only use once

Section titled “7. Don’t add a dependency you’ll only use once”

A 50 KB lib for a single gradient effect is not a fair trade. Inspect the route’s chunk with a Vite/rollup bundle visualizer (e.g. rollup-plugin-visualizer against the operator-vite build) before adding any dep over ~5 KB gzip and prove it’s worth the cost. (The old ANALYZE=true npm run build / @next/bundle-analyzer flow is gone with Next — @next/bundle-analyzer is not installed, and apps/operator’s build script just runs the operator-docs Starlight build then the operator-vite Vite build.) Section titled “8. Always test under “Slow 4G” + “4× CPU throttle” in DevTools”

Soft rules — should follow

Section titled “Soft rules — should follow”

9. React.memo, useMemo, useCallback — only when measured to help

Section titled “9. React.memo, useMemo, useCallback — only when measured to help”

Premature memoization adds maintenance cost and rarely helps. The exceptions:

  • Components in a virtualized list (always memo).
  • Components that pass props down a deep tree (memo + stable refs).
  • Computations > 1 ms (useMemo). Profile first.

For everything else, React’s reconciler is fast enough. Don’t useCallback every event handler “just in case.”

10. Use useDeferredValue and useTransition for slow updates

Section titled “10. Use useDeferredValue and useTransition for slow updates”

If a search input filters a 500-row table, the typing should feel snappy and the filtering can lag a few ms. Wrap the filter in useDeferredValue(query); the input updates immediately, the table updates when there’s an idle frame.

11. Co-locate slow data fetches with <Suspense> boundaries

Section titled “11. Co-locate slow data fetches with <Suspense> boundaries”

A page that needs both a fast and a slow data source should stream — the fast part renders, the slow part shows a skeleton. Don’t block the whole page on the slowest fetch.

12. Use the next/image shim (@/lib/router-compat) for any non-icon image, and always set explicit dimensions

Section titled “12. Use the next/image shim (@/lib/router-compat) for any non-icon image, and always set explicit dimensions”

The next/image import resolves to the router-compat shim (apps/operator/lib/router-compat), not Next’s optimizer — there is no Next image server in the SPA. Whichever <img>/<Image> you use, set explicit width/height (or an aspect-ratio box) and loading="lazy" for below-the-fold images. A bare <img> with no reserved box is a guaranteed CLS regression.

13. Move heavy CPU work to a Web Worker

Section titled “13. Move heavy CPU work to a Web Worker”

Anything > 50 ms of synchronous JS work blocks user input. Examples that should be in a worker, not the main thread:

  • Markdown / code highlighting (we currently do this on main thread — known TODO)
  • JSON-Schema → form converter for huge schemas
  • Search index building
  • CSV / large-payload parsing

The pattern: new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' }).

Network / data rules

Section titled “Network / data rules”

16. Use the local cache before the network

Section titled “16. Use the local cache before the network”

useSyncQuery (libs/generic/sync) is a transport-agnostic data hook — it works in any transport mode. On the Zero/WebSocket transport it gives us local-first, optimistic reads from the replica; on polling/SSE transports it falls back to REST. Don’t bypass it with a raw fetch for data the active transport already serves. Spinners on data we already have locally are a UX bug.

Mutations follow the same split: useSyncMutate(path, restFallback) runs optimistically through the Zero client only on the WebSocket transport (instant local apply, then server reconcile/rollback); on polling/SSE — where there is no Zero client — it calls your restFallback. Pass a stable restFallback so the same call site is REST-correct today and becomes optimistic for free once a WS provider is mounted. (Note: no @rocicorp/zero dependency is declared in any package.json — Zero is one configured transport, not a hard dependency of the hook.)

17. Pre-fetch the next likely route

Section titled “17. Pre-fetch the next likely route”

If clicking the harness picker is going to navigate to a different harness, use a TanStack <Link> (via the router-compat shim) so its chunk can be preloaded before the click. TanStack Router preloads on intent (hover/touch) when configured; keep navigation as <Link> elements rather than imperative router.push / navigate(), which don’t get the same preload behavior.

18. Cache server responses appropriately

Section titled “18. Cache server responses appropriately”

Cache-Control: max-age=... on idempotent GET endpoints. SWR semantics where appropriate. Zero takes care of most of this for harness data; keep it consistent for new endpoints.

19. preconnect to cross-origin API hosts

Section titled “19. preconnect to cross-origin API hosts”

For Anthropic, Cloudflare, Chatwoot, etc., add <link rel="preconnect" href="https://api.anthropic.com"> in the SPA’s root HTML (apps/operator-vite/index.html <head>, or the root layout component). Buys you 100–300 ms on the first request.

Layout / paint rules

20. Avoid layout thrash (read → write → read in the same frame)

Section titled “20. Avoid layout thrash (read → write → read in the same frame)”

Reading geometry (offsetWidth, getBoundingClientRect) after writing styles forces synchronous layout. Batch reads first, then writes.

21. Use transform: translate3d(0,0,0) to promote heavy elements to their own layer

Section titled “21. Use transform: translate3d(0,0,0) to promote heavy elements to their own layer”

Only for confirmed-hot elements (a moving canvas, a live-updating chart). Don’t sprinkle it everywhere — too many compositor layers tank GPU memory.

22. Avoid box-shadows on scrolling elements

Section titled “22. Avoid box-shadows on scrolling elements”

Box-shadow forces re-paint on every scroll frame. If you need a shadow on a sticky header, animate via transform: translateZ(0) + a static shadow, or use filter: drop-shadow which is sometimes composited.

Anti-patterns we’ve fallen into before — frontend

Section titled “Anti-patterns we’ve fallen into before — frontend”

These are real frontend regressions we’ve shipped and reverted:

  1. Spinning loaders for data we already have locally — fixed for IssuesList in 2026-05-02 (now shows “No issues” instead of spinner). If you find another, kill the spinner.
  2. Using setState in a tight loop instead of batching — caused chat panel scroll jank. Pattern: collect updates, set once.
  3. Importing the entire lodash for one helper — pulled in 70 KB gzip. Use lodash-es per-function, or just write the helper inline (most “lodash helpers” are 3 lines).
  4. Animating height/width on a panel slide — caused dropped frames. Switched to transform: translateY.
  5. Not memoizing RichGrid rows — caused 200ms commits when status changed in any row. Added React.memo.
  6. Fetching the same plugin manifest from 12 components — Zero deduplicates this for us; trust the cache.

What NOT to do — server-side / data layer

Section titled “What NOT to do — server-side / data layer”

The 2026-05-03 perf audit found these patterns had been shipped and were causing the dashboard’s TTFB to be ~19 seconds on localhost. Each one is now in the “do not repeat” list:

A1. Don’t await filesystem operations in a serial for loop

Section titled “A1. Don’t await filesystem operations in a serial for loop”

If you read N files sequentially, the per-call latency multiplies: in the audited environment ~150ms per fs.readFile × 68 files = 10 seconds just from the loop shape, where the same code parallelized was ~14ms. (The audit measured this under the old Next.js dev server, whose HMR file-tracking instrumentation wrapped every fs call; that named cause is stale — dev now runs the Vite SPA on :3055 plus a tsx/Hono host on :3070, with no Next dev server wrapping fs. The parallelize-the-reads advice still stands regardless of the runtime.)

Why this matters even in production: it’s still wasteful, just less catastrophically so. Always parallelize independent fs reads.

A2. Don’t open one Postgres pool per slug in a serial loop

Section titled “A2. Don’t open one Postgres pool per slug in a serial loop”

getHarnessPg(slug) opens a postgres-js pool with max=1 per harness. With ~70 registered projects, calling getHarnessPg(p.slug) in a loop opens 70 sequential connections × ~80ms each = 5+ seconds per request. Found at harness.get('/projects') — used to fire every 30s via autoloop AND every dashboard load.

Best: use the cross-harness harness_shared.harness_features_consolidated view (one admin pool, one query) instead of N per-harness pool opens. See memory: harness_features cross-harness view.

A3. Don’t introduce a heavy and a lite endpoint and have hot paths use the heavy one

Section titled “A3. Don’t introduce a heavy and a lite endpoint and have hot paths use the heavy one”

/api/harness/projects does N×PG-pool-open enrichment per project; /api/harness/projects/lite returns the same shape minus the enrichment. Audit found 5+ seconds per call, hit on every harness page load (including SSR) and every 30-second autoloop tick. A /lite endpoint is a smell signal: anywhere a callsite uses the heavy version “just in case,” it likely doesn’t need the enrichment. Default to lite, justify each upgrade.

A4. Don’t shell out to psql / pg_dump from runtime code

Section titled “A4. Don’t shell out to psql / pg_dump from runtime code”

Replaced with postgres-js + @electric-sql/pglite-tools in 2026-05-03 (commits a979073, 0915a96, 599755d). If you find yourself wanting spawn('psql', ...), you almost certainly want postgres-js’s sql.unsafe(text) for SQL apply or sql\COPY … TO STDOUT`.readable()for COPY. (Historical note: the lint guard and the one allowlistedpg-dump.tsdev-fallback exception lived in the@papercusp/export-statepackage —libs/papercusp-export-stateno longer exists; that package has been retired to_retired/snapshot-system/papercusp-export-state/`, so the cited guard path is dead.)

A5. Don’t put module-init side effects on a hot, re-evaluated path

Section titled “A5. Don’t put module-init side effects on a hot, re-evaluated path”

Artifact moved. The original offender was a Next.js catch-all route, apps/operator/app/api/[[...route]]/route.ts, with mountPluginApiRoutes(plugins).then(log) at module top level — re-evaluated per request by Next dev, producing [plugin-mount] log spam. That route is gone (apps/operator/app/api/ is empty), and mountPluginApiRoutes().then(...) now lives in the one-time boot script apps/operator/bin/host-bootstrap.ts (the Hono host), so the “re-evaluated per request” premise no longer applies.

The lesson generalizes: keep boot-time side effects (route mounting, pool warmup, log statements) in a script that runs once at process start, not at module top level on a path that can be re-imported/re-evaluated. If a .then(log) runs on every request, you’ve put init work somewhere hot. Guard it behind a “first call” papercup or hoist it into the host bootstrap.

A6. Don’t use <details> to gate “lazy” rendering

Section titled “A6. Don’t use <details> to gate “lazy” rendering”

Native <details> keeps its children mounted in the DOM regardless of open; the browser only toggles visibility. A <details>-wrapped 21-row × 100-<option> table costs the same as an always-open one. Use the LazyDetails component (apps/operator/app/_components/LazyDetails.tsx) which actually defers child mount until first toggle-open.

A7. Don’t poll on a 500ms cadence “for safety”

Section titled “A7. Don’t poll on a 500ms cadence “for safety””

Polling cadences should match the data’s actual change rate. A 500ms poll for system-voice-list arrival (changes once per page lifetime) is wasted CPU at best, render storm at worst. Cap at 5 attempts then stop. For ongoing polling (action log, scoper-result), use 4s while-something-active / 30s otherwise.

A8. Don’t push the same id twice into a render-key list

Section titled “A8. Don’t push the same id twice into a render-key list”

This freezes the dashboard: React’s “two children with same key” Console Error fires Next.js’s error overlay, which fires Fast Refresh full-reload, which re-renders → same error → infinite loop. Real incident on 2026-05-03; took the dashboard offline. Always grep for id: 'YOUR_ID' and key="YOUR_KEY" before adding to a registered-list pattern.

A9. Don’t dynamic-import inside a hot loop

Section titled “A9. Don’t dynamic-import inside a hot loop”

Module imports are cached but the .then() chain in a loop still adds promise-microtask overhead per iteration. Hoist all dynamic imports to module scope or hoist them above the loop.

A10. Radix Dialog focus-trap leaks pointer-events — guard with !important

Section titled “A10. Radix Dialog focus-trap leaks pointer-events — guard with !important”

Radix’s Dialog/cmdk/Modal mount sets two inline styles for focus-scope locking, and doesn’t always remove them on close:

  1. pointer-events: auto on Dialog.Content — meant to override an ancestor’s pointer-events: none. Leftover after close → the closed dialog intercepts every click on the page (<html> intercepts pointer events is the verdict-cli signature).
  2. pointer-events: none on <body> — meant to focus-trap users inside the dialog. Leftover after close → the entire page is unclickable until full reload; appears to the user as “totally frozen.”

Both have the same fix: !important on the override CSS so the leftover inline style cannot win. We’ve hit each one separately:

Dialogs still trap focus correctly via aria-modal / aria-hidden on their portal overlays, so neither override weakens modal UX — they just unfreeze the page when the lock leaks.

A11. Don’t fan out from N useEffect hooks fetching the same endpoint

Section titled “A11. Don’t fan out from N useEffect hooks fetching the same endpoint”

The audit captured /checkpoints ×2, /reviews ×3, /agents ×2 in a single dashboard load — one fetch per useEffect-mount, no dedup. In the audited environment each request also paid a 1-2s baseline overhead (then under Next.js dev; that named cause is stale now that the API is served by the Hono host on :3070). Cumulative: 30-60s of wasted server work on page load. The duplicate-fetch problem is runtime-independent — fan-out from N effects to the same endpoint is wasteful on any backend.

Pattern to use: one useSyncQuery in a parent component, propagate via context or props. Or migrate to Zero (already wired for many of these tables).

A12. (Historical — Next removed) Don’t carry flag-style config across major framework upgrades

Section titled “A12. (Historical — Next removed) Don’t carry flag-style config across major framework upgrades”

No longer applies to this stack. Next.js has been removed, so there is no next.config and no experimental.* flags to audit. Kept as a general lesson.

The original incident: experimental.turbopackFileSystemCacheForDev: false was set for a Next 15 Turbopack bug; Next 16 didn’t recognize it (⨯ turbopackFileSystemCacheForDev at boot). The transferable rule: when you bump any build tool across a major version (now Vite/rollup rather than Next), re-audit flag-style config you set to work around an old version’s bug and drop anything the new version warns about.

A17. Don’t fetch the same per-slug data N times in a Promise.all that varies by sub-key

Section titled “A17. Don’t fetch the same per-slug data N times in a Promise.all that varies by sub-key”

The /api/harness/<slug>/phases handler ran parseFeatures(scopedProject) inside Promise.all(PHASE_ORDER.map((p) => computePhaseInfo(...))). The features query returns the same data for all 3 phases (slug doesn’t change), but the per-harness PG pool’s max=1 cap meant each Promise.all branch sat in a queue waiting for a connection. Three sequential 5s queries in flight = 15s.

Fix: hoist invariant fetches OUT of the per-iteration loop. One query, pass the result to all branches.

Sounds obvious in isolation but easy to miss when the per-iteration helper hides the fetch. Same pattern as A15 (request-scoped cache) but at a higher level — A15 dedupes WITHIN a single resolveEnv-style helper; A17 dedupes ACROSS calls to the same helper that share an invariant input.

A18. Don’t pin per-process caches to module scope without a globalThis papercup

Section titled “A18. Don’t pin per-process caches to module scope without a globalThis papercup”

Caches declared const __cache = new Map() at module top level look durable but reset every time the runtime re-evaluates the module (historically visible as repeated [plugin-mount] log lines under the old Next.js dev catch-all route; any HMR / module-reload setup can do this). The cache key looks like a key but it’s effectively per-request because the Map itself is re-allocated.

Fix: pin the cache on globalThis so HMR / module re-eval reuses the same Map.

This is the durable-cache idiom commonly used for things like a Postgres connection pool. Use it for any Map/cache you want to survive across module re-evals in dev mode.

A19. Don’t shell-walk /proc per request without a cache

Section titled “A19. Don’t shell-walk /proc per request without a cache”

Walking /proc to find live processes (e.g., to compute alive state for a harness) means N+ sync readFileSync calls per request, where N is the total process count on the host (4000+ on a busy dev box). In standalone Node this is ~50-100ms; under the old Next.js dev fs instrumentation the audit saw 5-10 seconds (that named cause is stale now that the host runs under tsx/Hono, but the per-request /proc walk is still wasteful enough to cache).

Fix: 5-second globalThis-pinned cache (alive state doesn’t need sub-second freshness).

For dashboard “is this thing running?” status indicators, 5 seconds is well within the user’s tolerance. Don’t force the user to wait fresh-data each tick.

A16. Don’t enforce a minimum-visible debounce on a progress indicator

Section titled “A16. Don’t enforce a minimum-visible debounce on a progress indicator”

The route progress bar (@bprogress/react, driven by RouteProgressProvider) shows a loading bar during route changes. Its timing constants now live in apps/operator/app/_components/routePending.ts:

Per-target min-visible (the one intentional exception): the min-visible debounce is 0ms for generic routes but 360ms specifically for /harness/* navigations; routePendingMinVisibleMs() picks per target. So the “always 0” rule below holds for ordinary navigation, with the harness floor as the documented, deliberate carve-out.

A “minimum-visible debounce” on a progress bar conflates two things:

  • Anti-flicker (the bar shouldn’t appear and disappear within a single frame for instant routes) — bprogress already debounces sub-frame transitions internally, so this isn’t the caller’s job.
  • Padding the perceived load time (showing the bar longer than reality so the user “feels” something happened) — this is the opposite of useful. The bar lingering after content lands looks like a stuck navigation.

Always let the progress indicator reflect actual state. If you find yourself adding MIN_VISIBLE_MS to a polling/loading UI element, that’s the smell.

Same shape applies to spinners (don’t show them for >150ms after the data arrives) and skeletons (swap them out the moment the real content is ready, not on a fade-timer).

A15. Don’t read the same JSON file repeatedly within one request

Section titled “A15. Don’t read the same JSON file repeatedly within one request”

Even after parallelizing per-A1, hot endpoints often read the same plugin-config or env-config file multiple times in one request. The /branch/<x>/actions endpoint discovered this: a manifest with 5 env entries from @papercupai/cloudflare-pages.json would do 5 separate fs.readFile calls. Multiply by N actions per request and you have NM redundant reads.

Fix: pass a request-scoped Map<string, Promise<unknown>> cache through to all the resolution helpers; first reader populates, subsequent readers reuse the same Promise.

Measured: /branch/<x>/actions 1.5–3s → 30–590ms (warm 30ms; ~100× per-request speedup on the read fan-out).

The pattern generalizes to any “look up a config field” path called repeatedly per request: pass a Map; let the first reader pay the cost; let everyone else reuse the Promise.

Recurring patterns observed across all the fixes

Section titled “Recurring patterns observed across all the fixes”

Eight separate slow endpoints reduced to two root patterns:

  1. Serial fs/PG reads in a loop (A1, A2, A9) — eight callsites, each producing 5–25s of dead time. Promise.all collapses them to single-call latency. The fact that this happened EVERYWHERE (operator, libraries, deeply nested) is a signal that the synchronous-mental-model leaks into async code by default. Treat any new loop-with-await as suspect.

  2. Repeated reads of the same file/config within one request (A15) — even after parallelizing, the same file gets read N times when N actions reference it. A request-scoped Map cache turns N×M reads into N+1.

A third pattern is harder to catch but biggest in absolute pain:

  1. Radix focus-trap inline-style leaks (A10) — twice in one session, the page went “totally frozen” because Radix left a pointer-events inline style on a DOM element after the dialog closed. Both leaks were on different elements (.h-cmd and <body>) but had the same root: Radix lifecycle bugs we don’t control. The fix is always !important on the override CSS; trust the dialog’s aria-modal for actual focus-trap semantics.

What this session demonstrated

Section titled “What this session demonstrated”
  • 20-second mystery endpoints are usually one of the patterns above. Don’t reach for “the dev server is just slow” (the audit’s original culprit was Next.js dev, now retired); instrument the handler with t0/t1 markers, find the actual bottleneck, parallelize.
  • The /lite endpoint pattern is a smell. If you have /things and /things/lite, every callsite using /things “just in case” is overpaying. Default to /lite; justify each upgrade.
  • Lint guards beat memory. Patterns added to perf-anti-patterns.test.ts are caught at CI time. Patterns that only live in this doc require humans to remember.
  • The BASELINE ratchet works. Started at 9 grandfathered offenders, now at 1. The stale-baseline check forces the list to shrink as fixes land, so this isn’t “permanent debt” — it’s a queue.

Cheat sheet — what to do, in order

Section titled “Cheat sheet — what to do, in order”

When you’re about to write or change a component:

  1. Is everything in this chunk actually needed up front? Code-split the heavy, not-immediately-visible parts (dynamic shim / React.lazy). (No Server Components on this SPA — there’s no “make it server-only” option.)
  2. Did you accidentally pull a host-only module (Postgres, node:fs, credentials) into the client tree? Keep it on the Hono side; cross via the API.
  3. Will it render in a list of more than 50 items? Virtualize and memoize.
  4. Does it have an animation? CSS first; auto-animate for lists; motion last.
  5. Does it fetch data? Use useSyncQuery (transport-agnostic) or <Suspense>. Optimistic via useSyncMutate on the WS transport.
  6. Did you measure with React DevTools Profiler? Do it before merging.

Adopting these is what makes the difference between “okay app” and “feels like Linear.” Every rule on this page came from a real regression we’ve shipped or fixed; none of them are speculative.
