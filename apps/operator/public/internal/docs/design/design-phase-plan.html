1. Why a phase, not a tag

Section titled “1. Why a phase, not a tag”

Tags are orthogonal grouping (which features share memory). Phases are sequential states with gates and deliverables. Design has both. Every feature with a user-facing surface needs design before implementation, then again as review after; that’s a workflow, not a label.

A separate Design tab is justified because the working surface is different from the dashboard’s: queues, mocks, tokens, registry, visual diff. The data spine is shared with the dashboard’s Features component (see §6).

2. Lifecycle integration

Section titled “2. Lifecycle integration”

Design reuses the existing card lifecycle vocabulary (pending / accepted / ignored). It does not introduce new state names. The phase is the axis of difference, not the state machine.

A feature record gains:

pending covers both “awaiting designer spawn” and “designer in flight” — the implementation lifecycle treats spawned-but-unfinished the same way.

ignored is overloaded: it can mean “phase explicitly skipped” (this feature doesn’t need design) or “feature dropped” (no design will happen because the feature is dead). The two are conflated because the gate behavior is identical (no spec required to advance or close). If telemetry needs to distinguish, use the existing feature-lifecycle status to disambiguate.

Gate: a feature cannot transition into the implementing phase until designStatus ∈ { accepted, ignored }.

4. Roles

4.1 Designer agent

Section titled “4.1 Designer agent”

Output is a specification, not edited components. To enforce this, the runtime restricts designer commits to a per-adapter allowlist (default: design/, apps/operator-docs/src/content/docs/design/, sketch artifact paths). Commits outside the allowlist are rejected with a clear error and the designer is re-prompted, not killed.

If a designer legitimately needs to scaffold something outside the allowlist (e.g., a token JSON proposal in a custom path), the designer requests an allowlist extension via a special spec annotation; orchestrator (or human) approves.

Deliverables per feature:

  • A UI IR document (see §7) describing the surface
  • Token decisions (which existing tokens, any new ones — §9)
  • Component contract: which registry components to use, with which variants and props
  • Copy (labels, empty states, error messages)
  • Interaction states (hover/focus/disabled/loading/error)

Inputs:

  • The feature record (description, acceptance criteria)

  • Token store (§9)
  • Adjacent design memos under apps/operator-docs/src/content/docs/design/

4.2 Design reviewer (lightweight)

Section titled “4.2 Design reviewer (lightweight)”

After implementation ships, a review pass compares the rendered surface to the spec. Output is either approved or a re-opened design card with the diff.

If the reviewer rejects, a fresh designer agent is spawned with: the rejected spec, the rendered diff, and the reviewer’s notes as new input. The original designer’s spec is preserved as an artifact for traceability — never overwritten.

Reviewer is the same agent persona as the designer with a different prompt; one binary, two roles.

After a rejected design, a back-off timer prevents immediate re-spawn (default 1 hour, configurable). Rejection reasons feed the next prompt so the designer doesn’t repeat the mistake.

7. The UI IR — JSON shape, ecosystem-agnostic

Section titled “7. The UI IR — JSON shape, ecosystem-agnostic”

This is the most important architectural decision in the plan.

The designer agent emits a semantic tree that implementer adapters resolve into their idioms. It must not emit JSX, Tailwind classes, Qt XML, or any ecosystem-specific syntax.

7.1 Why JSON, not a custom DSL

Section titled “7.1 Why JSON, not a custom DSL”

We considered copying Slint’s syntax (a real declarative DSL with parser/typechecker/LSP) versus a JSON schema. JSON wins unambiguously because the IR’s primary author and primary consumer are both LLMs:

DSL (Slint-like)JSON IR
Time to v0.13–4 months2–3 weeks
LLM emission qualityMid; needs many-shotNative
Free toolingNone (write parser/LSP/diff)jq, JSON Patch, JSON Schema, IDE support
Adapter complexityParse → AST → walkConsume object directly
Refactoring costTouches parser + adaptersBump irVersion, ship transformer

A DSL’s main benefit (human readability) doesn’t apply when humans aren’t the primary authors. Costs (parser, LSP, agent prompt overhead, two-layer adapter parsing) all do.

Hybrid escape hatch (Vega-Lite/Altair pattern): if a real human-authoring use case ever emerges, ship a thin DSL surface that compiles to the same JSON. We never lose the option.

7.2 Schema language: JSON Schema (default), CUE (option)

Section titled “7.2 Schema language: JSON Schema (default), CUE (option)”

JSON Schema is universally understood and trivial to validate in every language. CUE is stronger — real type system, better constraint expression — and is worth considering once the IR stabilizes. Start with JSON Schema; migrate to CUE if/when limits bite.

Properties of this format:

  • No DOM assumptions. kind: "stack" becomes flexbox, QVBoxLayout, or Vertical { } depending on adapter.

7.4 Sub-IR escape hatch — Plotly for charts

Section titled “7.4 Sub-IR escape hatch — Plotly for charts”

Charts are a domain that already has a mature multi-language declarative spec. We don’t reinvent it.

Designer agent reaches for kind: "chart" only when the surface genuinely includes data viz; otherwise compose primitives.

Plotly chosen over Vega-Lite, ECharts, ApexCharts after survey:

  • Most language bindings of any chart spec — JS, Python, R, Julia, MATLAB, F#, .NET. Directly serves the cross-ecosystem goal.
  • Most LLM training data (pervasive in data-science notebooks); agents emit it more reliably.
  • Verbose but explicit; agents don’t care about character count, and explicit specs are easier to validate and diff.
  • 18.2k★, large active community.

Vega-Lite’s grammar-of-graphics elegance matters when humans compose specs by hand — wrong axis to optimize for an agent-authored format.

7.5 No card / form sub-IR

Section titled “7.5 No card / form sub-IR”

Earlier drafts proposed embedding Adaptive Cards as a card sub-IR. On closer look, AC’s unique value is its multi-stack external renderer ecosystem (Teams, Outlook actionable messages, Bot Framework). For our internal cards/forms/dashboards, embedding AC adds a dependency without saving work and constrains us to AC’s bounded vocabulary.

The IR’s general kind: "card" / kind: "form" is rendered by the ecosystem adapter. Adapters may implement their renderer using libraries like JSON Forms, react-jsonschema-form, or Formily — that’s an adapter detail, not an IR-level decision.

Section titled “7.6 Iconography”

7.12 Composition: surface vs route

Section titled “7.12 Composition: surface vs route”

A surface is one IR document. A route is a thin manifest that lists surfaces (and their layout — split-pane, tabs, modal stack). Route manifests are a separate JSON shape, much smaller than surface IR. Designer authors a route spec when adding/changing navigation; otherwise just surfaces.

7.13 Data binding boundary

Section titled “7.13 Data binding boundary”

The IR declares slots and binding points; it does not declare data sources. A list says “this is a list, items repeat, each item gets slots A B C”; the implementer wires the data source.

shape is a named type the implementer maps to its data layer (TypeScript type, Rust struct, etc.). The designer doesn’t pick the data source; the implementer does.

7.15 IR linter (anti-pattern checks)

Section titled “7.15 IR linter (anti-pattern checks)”

A validator says “is this valid JSON matching the schema?”. A linter says “is this good IR?”. Both run on every submitted spec. Lint rules (open-ended, expand as patterns emerge):

  • Maximum nesting depth (default 6)
  • Every interactive element has an a11y.role or maps to a registry component that supplies one
  • No literal colors / dimensions outside tokens.uses references
  • Every states.error has a recovery action (retry, navigate)
  • Every states.loading has an aria-live equivalent
  • surface is unique within the harness
  • Registry component IDs all resolve in the active registry
  • Token IDs all resolve in the active DTCG store

Linter runs at submit time; warnings flow to the design crit prompt; errors block acceptance until fixed.

9. Tokens — DTCG as canonical, per-ecosystem outputs

Section titled “9. Tokens — DTCG as canonical, per-ecosystem outputs”

The W3C Design Tokens Community Group format (design-tokens.org) is the cross-ecosystem standard JSON for tokens. It is deliberately neutral: color, dimension, typography, duration, etc.

Adopt DTCG as the canonical token store under design/tokens/. As shipped, the canonical DTCG store file is design/tokens/base.json — the runtime sync-resolver, the list_tokens MCP tool, and the Design tab’s Token pane all read it directly. The seeder writes a sibling design/tokens/seeded-from-harness-css.json as the input to the manual semantic pass (§20.13), which merges into base.json. Per-ecosystem transformers emit:

  • CSS custom properties for React/Tauri
  • Tailwind preset
  • .qss for Qt
  • Theme structs for egui / iced
  • .slint for Slint
  • Anything the adapter author writes

Transformer choice: Terrazzo (DTCG-native, modern) or Style Dictionary (battle-tested, Amazon). Terrazzo is the recommended default for new code; Style Dictionary remains a fine choice for adapters that need the wider transform ecosystem.

As shipped: the repo-level npm run tokens build runs on Style Dictionary v4 (^4.4.0, config in design-tokens/style-dictionary.config.mjs) — not Terrazzo. The react-tailwind adapter, on a separate path, ships its own minimal in-house CSS-vars + Tailwind-preset emitter (its docstring notes Terrazzo “is not yet a dep”). Terrazzo remains the planned long-term transformer but is not currently a dependency.

This solves the existing harness.css triplication problem (operator + libs/papercusp + libs/git-graph) as a side effect: single source, generated outputs.

16. Implementer-side IR consumption

Section titled “16. Implementer-side IR consumption”

Implementer agents are upgraded to consume IR. Two protocol options considered; we ship (b) first.

(a) Code-emit fast path — adapter’s codeEmit.fromIR() produces scaffold files, implementer edits them. Faster but the implementer loses understanding of why code looks the way it does.

(b) IR-as-context — implementer prompt includes the IR JSON + the adapter’s “how to translate IR into this ecosystem” rules. Implementer writes code by hand, referring to IR. Slower per feature but produces higher-quality, idiomatic code; implementer internalizes the design intent.

Path (b) is the default. Path (a) is opt-in for high-volume CRUD features where idiomaticity matters less than throughput.

The implementer prompt gains a section: “the design spec is the source of truth for what to build; deviations require a new designer pass, not silent edits.”

  • Stagewise — dev-tool not design-tool; revisit for the review pass if useful
  • bolt.new / bolt.diy — wrong altitude
  • Cross-app consistency audit pane — defer until tokens are unified via DTCG

16. Build order

Section titled “16. Build order”

Each step is independently shippable.

  1. Schema + lifecycle fields + gate. Add the design lifecycle columns (needs_design, design_status, design_spec_id, discarded_design_work) to the canonical features table harness_shared.harness_features_consolidated, plus the harness_shared.harness_design_artifacts table (with Zero sync). (Shipped as columns on the consolidated table, not a separate harness_design_phase table.) Heuristic at creation. Gate before implementing. No UI yet.
  2. Design tab shell with Features pane only (mode=design). Three-column layout (§6.1). Validates the mode parameter abstraction.
  3. DESIGN_SPEC.md template + fallback chain + designer agent prompt rooted in it. Designer can produce a free-form spec (no IR yet).
  4. UI IR v0.1 — minimal JSON Schema, hand-written examples, validator + linter (§7.6). Designer agent emits IR; no consumer yet.
  5. Ecosystem Adapter Contract + plugin shape. Empty registry of adapters.
  6. papercusp-design-react-tailwind adapter, capabilities: registry, tokens (Tailwind), codeEmit. Implementer agent prompt updated to consume IR.
  7. DTCG token store under design/tokens/. Token-extraction seeder runs once over the operator’s harness.css triplets to produce the initial DTCG file (the eat-our-own-dogfood case; community adapters define their own seeders). Adapter emits Tailwind preset + CSS vars. harness.css files are migrated incrementally (see §20.13).
  8. Component registry browser pane (Design tab). Reads from the adapter.
  9. Token inventory pane + new-token proposal flow (§9.1).
  10. Storybook preview adapter — captures stories as examples for the registry; powers the preview pane.
  11. tldraw sketch pane + artifact storage.
  12. Lost Pixel in CI; visual regression strip pane; baseline-approval action (§12.1).
  13. Design memos pane — surface existing .mdx memos with status; promote-to-feature action (§17.3).
  14. Reviewer agent + post-ship review pass + design-crit agent role (§20.9).
  15. Mock-input adapters (Figma, screenshot, tldraw-derived). Optional; opt-in per feature.
  16. Export adapters (Adaptive Cards, Slack Block Kit). Optional; opt-in per feature.

Steps 1–4 are the spine. Steps 5–6 are the abstraction proof. Everything after is panes and adapters that hang off the spine.

20. Resolved decisions

Section titled “20. Resolved decisions”

20.1 Model selection per role

Section titled “20.1 Model selection per role”

Configurable per-harness with sensible defaults:

  • Designer: best available reasoning model (Opus class)
  • Crit: same family as designer (apples-to-apples comparison)
  • Reviewer: mid-tier (Sonnet class) — pattern-matching task
  • Implementer: unchanged from existing config

Override via DESIGN_SPEC.md frontmatter: models: { designer: "...", reviewer: "...", crit: "..." }.

20.2 Adapter lifecycle and conflict

Section titled “20.2 Adapter lifecycle and conflict”
  • Adapters activate lazily — on first reference (feature creation triggers heuristic scan; spec submission triggers code-emit)
  • Manifest declares claims: ["react-tailwind"]; if two installed adapters claim the same ecosystem, harness must explicitly pick one in harness.config.json (design.activeAdapters: { ... })
  • Conflict surfaces as an operator directive, not a silent pick

20.3 Permission / sandbox model

Section titled “20.3 Permission / sandbox model”

Reuses papercusp’s existing plugin permission grants. Design-phase permissions:

  • read:registry (always granted)
  • read:design-tokens (always granted)
  • write:design-artifacts (always granted for designer agents)
  • read:current-surface (granted for redesigns)
  • propose:tokens (granted for designer agents)
  • external-call:<targetId> (per-export-adapter; user grants on install)

Adapters cannot scan paths outside their declared sourcePaths without an additional grant.

20.4 Designer-in-flight visibility

Section titled “20.4 Designer-in-flight visibility”

Happy path stays out of operator directives. The feature card shows a small “designing” badge with elapsed time + token count. Operator directive only fires for the cases listed in §6.3 (deadlock, escalation, rejection, new-token proposal).

20.5 Concurrent edits / locking

Section titled “20.5 Concurrent edits / locking”
  • DTCG token store: optimistic locking with version field; conflicts surface a “merge needed” operator directive
  • Registry entries: read-only at the IR layer (only adapters write, during scans, with a global advisory lock per ecosystem)
  • Design specs: per-feature, no concurrent designers on one feature (the N=2-3 happens before any spec is accepted)

20.6 Cost telemetry per spec

Section titled “20.6 Cost telemetry per spec”

Every spec artifact records tokensIn, tokensOut, costUsd, modelId, elapsedMs — same shape the rest of the runtime uses. Surfaced in the design tab’s right rail per feature; aggregated in the existing budget views.

20.7 Lost Pixel intentional-vs-regression

Section titled “20.7 Lost Pixel intentional-vs-regression”

Spec acceptance writes a targetBaselineHash to the design phase record. Lost Pixel diffs against the baseline; if the new hash matches targetBaselineHash, the diff is auto-approved as intended. Mismatches surface for human review. No silent baseline drift; intent is always declared.

20.8 Migration of existing UI

Section titled “20.8 Migration of existing UI”
  • Existing surfaces do NOT retroactively get IR specs (the migration would be bottomless)
  • New features: must produce IR if they create UI
  • Touched features: changing an existing surface requires authoring its IR first (one-time cost paid lazily)
  • The operator’s existing surfaces become ground-truth for designer training data — preview adapter can capture them as reference material

20.9 Multi-designer concurrency + design crit

Section titled “20.9 Multi-designer concurrency + design crit”

Hybrid; not PR-style merge.

  • Orchestrator spawns 2–3 designers in parallel; each emits a candidate spec
  • A design-crit agent (the reviewer agent’s persona, in “crit” mode) scores candidates against DESIGN_SPEC.md rubric and picks ONE as canonical, optionally cherry-picking notes / decisions from runners-up as annotations
  • Crit can deadlock (no clear winner); deadlock surfaces as an operator directive (§6.3) for human pick
  • Auto-merging specs is a trap — design choices need a single authorial voice or the result is incoherent
  • Default N=2; raise to 3 only when feature is high-stakes / orchestrator marks it exploratory
  • Rejected candidates kept as artifacts on the feature for later reference, not deleted

20.10 IR versioning

Section titled “20.10 IR versioning”
  • Schema lives in core papercusp; semver
  • Every spec carries irVersion: "0.3"; runtime ships upgrade transformers between minor versions
  • Adapters declare irVersionsSupported: ["0.x", "1.x"] in plugin manifest; orchestrator refuses to gate-promote a spec into an adapter that doesn’t claim its version
  • v1.0 lock criteria: at least 2 production adapters consuming IR for ≥1 month without a breaking change to the schema. Concrete bar; no fuzzy “mature enough.”
  • Ownership: core team for v1; lightweight RFC process afterward (the IR should stabilize fast)

20.11 Memo ↔ feature linkage

Section titled “20.11 Memo ↔ feature linkage”

Promotable, with light coupling.

  • Memo gets a “promote to feature” action → creates feature with the memo as initial spec source
  • Memo retains link as spawnedFeatures: [...]
  • Memo status (open / addressed / wontfix) lives on the memo regardless of promotion — a promoted memo flips to addressed when its feature ships
  • Don’t auto-promote; humans/orchestrator decide
  • Un-promoted memos stay advisory and surface in the design tab’s memo pane as backlog

20.12 Human override UX

Section titled “20.12 Human override UX”

No checkbox at creation (clutter). Surface override via the card itself.

  • Right-click card → “Skip design” / “Force design” — works in both Dashboard and Design tabs
  • Keyboard shortcut for the toggle: TBD by operator UX (single-key shortcut conflicts likely; defer naming until Design-tab integration lands)
  • If designer agent has already spawned, “Skip design” requires confirm + sets discardedDesignWork: true for telemetry
  • Status visible on every card as a small badge (design icon when needsDesign, struck-through when manually skipped) — no extra rows or modals
  • Heuristic should be right >90% of the time; override is an exception path, not first-class chrome

20.13 Token migration path

Section titled “20.13 Token migration path”

No magic extractor exists; we build a small one. Operator-specific plan; community adapters define equivalents for their CSS-or-not sources.

  • Step A — seeder script. Regex over the three harness.css files for :root custom properties → DTCG seed file. Tailwind configs (if present) convert almost trivially because they’re already structured.
  • Step B — manual semantic pass. Extracted tokens have technical names (--color-1, --space-md); a designer (human or agent) renames to semantic (color.bg.surface, space.gutter) and dedups. This is the hard part; no tool replaces it.
  • Step C — flip the imports. harness.css files become thin wrappers that @import the generated CSS vars from DTCG. Keep originals committed for one window.
  • Step D — Lost Pixel gate. Run regression across known routes; only delete the originals when the diff is empty.
  • Estimate: half a day of focused renaming for the operator harness; longer for libs/papercusp due to surface area.

21. Still-open questions

Section titled “21. Still-open questions”

These remain genuinely undecided and will resolve as we hit them.

  • Designer agent failure mode: if the designer can’t produce a valid IR (validation fails repeatedly), does the orchestrator escalate to a human, fall back to free-form spec, or skip the phase? Probably escalate, but TBD on UI.
  • IR ↔ implementation traceability: do generated files carry back-pointer comments to their source spec, or do we use a source-map-style sidecar (no comment noise in the code)? Lean sidecar.
  • Cross-harness design system sharing: when multiple harnesses share a libs/papercusp/-equivalent, do they also share a DTCG store and a registry, or do those stay per-harness with explicit extends syntax in the harness’s DESIGN_SPEC.md? Lean explicit extends, but defer until we hit the case.
  • Designer-agent web access: can designers query the live web for design references (color trends, ux patterns) or are they closed-world to memos + registry + DESIGN_SPEC.md? Closed-world is safer; web access is a separate capability gate per harness.
