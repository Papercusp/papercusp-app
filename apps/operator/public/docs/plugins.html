Plugins

A plugin extends what every harness can do: it adds dashboard tabs, toolbar actions, lifecycle hooks, scheduled routines, and database schemas. Plugins ship as standalone packages on the marketplace and install per-machine, then enable per-harness.

The reference plugins that ship with Papercusp — @papercupai/cloudflare-pages, @papercupai/slack-notifier, @papercupai/jira-sync, @papercupai/notion-export — are themselves just plugins published to the marketplace.

What a plugin can contribute

Section titled “What a plugin can contribute”

Plugins declare contributions in their manifest:

SurfaceWhat it isExample
dashboardTabsA tab that appears in the harness dashboarddocs-viewer adds a “Docs” iframe tab
sidebarItemsA link in the operator’s left sidebarLinear plugin adds “Linear”
harness-toolbar actionsA button next to “save snapshot” / “start”cloudflare-pages adds “Publish website”
lifecycle hooksCode that runs on mission.start, onFeaturePassed, etc.slack-notifier posts a message on mission.done
routinesScheduled triggers (cron / webhook / API)briefings runs daily at 9am
api routesPlugin-owned HTTP endpoints under /api/plugins/<name>/postgres-manager exposes /migrations/run
schemasPostgres DDL the plugin owns (run at install time)jira-sync owns plugin_jira.issues

Each of these is opt-in via a capability declaration. A plugin that wants to read secrets must list secrets:read:<NAME> (or secrets:read:PREFIX_*). A plugin that wants to fetch a URL must list http:fetch:<host> (or http:fetch:*.subdomain). The runtime refuses to load plugins whose declared capabilities don’t cover what the code actually does, and refuses to invoke handlers whose capabilities aren’t satisfied.

Lifecycle hooks

Section titled “Lifecycle hooks”

The host fires named hooks at well-known points. Subscribe in hooks: { ... } on the exported Plugin object:

HookWhen it firesReceives
onLoad(ctx) / onUnload(ctx)Plugin (un)loaded by the hostctx
beforeMissionStart(ctx)Once before the harness loop startsctx
afterDone(ctx)After the orchestrator decides DONEctx
onPostOrchestrator(ctx, decision)After every orchestrator invokectx, decision verb
onPostWorker(ctx, featureId)After every worker invokectx, featureId
onPostValidator(ctx, featureId, status)After every validatorctx, featureId, ‘passed’ | ‘failing’
onFeaturePassed(ctx, featureId)When a feature transitions to passedctx, featureId
onProposalAccepted(ctx, proposalPath)When a SPEC proposal is appliedctx, proposalPath

ctx carries the install slug, project paths, a logger, the plugin’s private storage path, the action registry, and a capability-gated spawn for invoking subprocess binaries.

Submitting to the marketplace

Section titled “Submitting to the marketplace”

Same flow as templates and snapshots: GitHub-OAuth on first publish under @your-handle/..., then papercusp publish from the plugin directory. After publish:

  • Listed under Plugins.
  • Operators install via the UI’s “Install” button or papercusp install @you/my-plugin.
  • Per-harness enablement happens in the marketplace’s “Enable in harness…” picker.

Tips

Section titled “Tips”
  • Compile to index.cjs, not index.js. If your package.json declares "type": "module", a .js file is treated as ESM and CommonJS module.exports won’t bind. The loader looks for .cjs first for exactly this reason.
  • Don’t import @papercusp/plugin-sdk types into bundles — mark it --external in esbuild. The host provides the types at runtime.
  • Declare every capability your code uses. The runtime refuses to fire any handler whose capabilities aren’t a subset of the plugin’s declared set. A compute:exec:ffmpeg call will throw if you forgot to list it.
  • ui:widget: "password" in your uiSchema marks a config field as sensitive. Snapshots redact those fields automatically. Use it for any token, key, or secret your plugin reads.
