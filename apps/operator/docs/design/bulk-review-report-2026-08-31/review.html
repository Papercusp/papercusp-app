The fix: every row states its action in the first column

Five moves. The row becomes a sentence you read left to right — verb, target, change, because — and the only chevron on the row belongs to the only thing that discloses.

  • Verb firstA coloured action chip in column one: Mark done, Clear blocker, Archive plan, Rewrite Now. Same vocabulary as the button that commits it.
  • Change, not badgesKeep the pills, but label the transition status and reserve the coloured "after" pill for the value Apply will write.
  • Honest chevronsConfidence becomes a non-interactive dot + word. A separate Why ▾ button opens the evidence. One chevron, on the disclosure.
  • Real linksThe slug opens the plan dashboard. It already looks like a link; make it one.
  • Per-row actionsAn overflow menu carries Apply just this, Skip, Re-check, Open plan — the four things the backend already supports and the report never offered.

Ask 2 — the run lifecycle

The re-run already exists. The report just never offers it.

This is the part that stings. /api/admin/plan-cleanup accepts stop, restart, resume, recheck-finding, dismiss-finding and reclassify. The progress strip wires up three of them. Then the run reaches review, the strip is replaced by the takeover, and the takeover's entire action set is Apply selected and Close.

Worse: two whole run outcomes have no screen at all

Both hosts render only when run.phase === 'review'. A run that auto-applied everything settles to complete — so the one run that actually changed the owner's plans without asking is the one run they can never open and inspect. A run that ends failed is equally invisible. There is no run history either: the only door to a past run is a ?opcln= URL nothing in the UI hands you.

A run-state bar, always present, directly under the header

One strip that states what the run is, how old it is, and what you can do to the run itself — as opposed to the findings inside it. It carries the controls the API already has. Six states; the owner never has to guess which one they're in.

The staleness guard needs a back-end half, not just a banner

applyPlanCleanupFinding calls setItemStatus with the target value and no expected-current value, so applying a three-day-old report silently overwrites whatever happened since. The write already returns oldStatus, so the cheap fix is to send the finding's recorded from as a precondition and let the route refuse the mismatch — that refusal is what feeds the changed since the scan row state above.

Ask 4 — Inbox parity

Same shell, same bugs, opposite gaps

The two flows already share ReviewReportShell, ReportTakeover and the row/group model — that part of the earlier work landed. What did not get shared is everything around the rows, and the two flows have drifted in opposite directions.

Plans clean-up has

  • Grouping by fix kind, and a per-group select-all
  • A transition (from → to) on every row
  • Nothing per-row: no retry, no skip, no re-check

Inbox bulk-resolve has

  • Per-row Retry, Dismiss and Reconcile, inline in the drill-in
  • A recommendation card with rationale and retry condition
  • No per-group verbs; the row's action lives inside the disclosure

Both gate on phase === 'review', so both lose their complete and failed runs. Both hide the resolver's liveness once the strip is replaced. Fixing either one twice would be the mistake — so the fix is to move three things up into the shared layer and let each flow supply only what is genuinely different.

  • 1 · useBulkRunOne hook over one route shape. use-plan-cleanup-run and use-inbox-bulk-run are the same lifecycle — start / stop / restart / resume / accept / dismiss / recheck — typed twice. Collapse to a generic keyed by runKind, and both flows inherit every lifecycle control at once.
  • 2 · RunLifecycleBarThe six-state bar above is pure function of phase + liveness + counts, all of which already exist on both runs. It belongs in review-report/ beside the shell, not in either consumer.
  • 3 · Row actionsAdd actions?: RowAction[] to ReviewReportRow — { id, label, verb, tone, run }. Inbox moves its Retry/Dismiss/Reconcile into it and gets the overflow menu for free; Plans passes Apply-one / Skip / Re-check and gets parity with Inbox on day one.
  • 4 · Host gateOne shared host that admits every phase and picks the presentation, instead of two copies of phase === 'review' that each drop two outcomes on the floor.

If you want it built

Four changes, in the order that de-risks them

Ordered so each one is shippable alone and the riskiest change lands on a surface the previous ones already made legible.

  • FirstRow legibility. Verb column, split confidence, real link, honest chevron. Pure presentation inside ReviewReportShell — no route changes, both flows benefit the moment it merges.
  • SecondOpen every phase. One shared host; complete and failed runs stop being invisible. Small, and it is the change that makes the auto-apply path auditable.
  • ThirdThe run-state bar and per-row actions. Wires the controls the API already exposes. This is where stopped mid-run stops being a dead end.
  • FourthThe staleness precondition. Send from as an expected-current value and refuse the mismatch. Touches the write path, so it goes last — on top of a report that can already show and re-check a stale row.
