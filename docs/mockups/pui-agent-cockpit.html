The task list · answering the TodoWrite question

An owned task tool, three ways

Claude Code's todo list and Codex's plan are harness tools — the model calls a tool the harness registers, and the harness's TUI renders it. Our loop ships none unless we build one. Models are heavily post-trained to reach for it on multi-step work, so we should — the question is how far to take it.

T1 — Session scratchpad (parity with Claude Code)

●●● pinned widget · collapses with ctrl-t
 TASKS 2/5 ─────────────────────────────────────────────────────
  ✓ reproduce scroll reset
  ✓ write failing test
  ▸ move offset into pane state
  ○ re-run affected suite
  ○ update work-item checkpoint

One tool + state on the session row, streamed as typed frames. Ephemeral — dies with the session, exactly like Claude Code's.

T2 — Ledger-bridged (the thing nobody else can do)

●●● same widget · bridged to the ledger
 TASKS 2/5 · bridged ──────────────────────────────────────────
  ✓ reproduce scroll reset
  ✓ write failing test            ⇗ WI-42107
  ▸ move offset into pane state    ⇗ WI-41759 · ckpt syncs
  ○ re-run affected suite
  ○ file follow-up: diff pane perf · shift-p → mint work-item

Todos can be promoted to work-items (and seeded from claimed plan items). Progress on a bridged todo writes the work-item checkpoint — the scratchpad and the durable ledger stop being two worlds.

T3 — no new tool (rejected, but worth naming)

  • Render claimed plan items + work-items as "the" task list; no ephemeral scratchpad.
  • Cleanest data story, but pushes models out-of-distribution — they expect a lightweight todo tool and will fight its absence with prose plans.

How it's wired (T1/T2)

  • One tool registered in the owned loop (ToolLoopAgent). Schema aliased per model family — todo-shaped for Anthropic models, update_plan-shaped for Codex models — so both stay in-distribution.
  • State on the PG session row → typed frames → widget. T2 adds handlers that write work_items / plan links.

Part two · the fleet · WI-42180

What pui does with the fleet

The Fleet tab was built in June. The fleet system it watches has been rebuilt underneath it since. Here is the gap, four directions to close it, and a straight answer on the kanban.

First · what is actually wired

The Fleet tab is watching a June fleet

apps/tui/src/fleet.rs states its own provenance in line 1: pui-fleet-status-view-2026-06-04. It is 1,878 lines and it is a good build — roster, dossier, plan burn-down, a curated/mirror toggle, a comms sub-view, and the staged-wake board next door in wake_board.rs. The problem is not quality. It is that the fleet grew a nervous system afterwards and nobody told the TUI.

Wired today

  • fleet:assignments — 17 call sites. Claims, load, intent, queued items, per-agent.
  • Roster presence, grouped by fleet, with a per-fleet colour.
  • Plan and work-item burn-down aggregated across live plans.
  • The wake board: release · edit & release · skip · release-all · toggle wake-mode. This is the one surface that already acts.
  • declared_unclaimed — the ⚠ badge for a declared-but-unclaimed lane.

Zero references in the entire crate

  • sessionState — the unified liveness verdict
  • contextPressure — how close a member is to losing everything it knows
  • fleet:leader-brief · fleet:invariant
  • claim specs and their revisions · scheduler:get_next
  • fleet:bench · blocked-by edges
  • every fleet transition event — member-dead, claim-released, item-completed, context-critical, drained, admission-blocked

The one that bites

pui's green dot is a heartbeat, not a verdict. agents_online is literally roster.filter(|r| !r.stale), and the legend offers three buckets of process-keepalive age: live <1m · idle <10m · stale ≥10m.

The shared oracle behind coord:presence answers a different and much better question — live | parked | draining | suspect | ended | recorded — and a warm-dead session reads heartbeatFresh:true with sessionState:'ended'. pui paints that agent green and counts it online. That is the exact "is it working or quietly dead?" failure, rendered as reassurance. Every direction below assumes this is fixed first — and it is a field swap, not a feature.

Same ten items, same plan, same moment. The left pane spends its entire width encoding one short enum; the right shows that enum in eight characters and spends what it saved on the three fields you'd actually go looking for.

Recommendation: don't port it. Keep it in the GUI.

Four reasons, in order of how much they matter:

  • The columns encode status, and status is the least interesting thing about a live fleet. It is one short enum. A list column renders it in eight characters and has room left for the holder, the context pressure, and the blocking edge — the fields you actually open the board to find.
  • Its interaction premise is drag. That is genuinely good with a pointer. In a terminal it becomes a keystroke, and a keystroke does not need columns to land in.
  • It is item-shaped and single-plan. There is nowhere on a kanban card to put an agent, and every interesting fleet fact is agent-shaped: who holds it, are they alive, are they about to lose their context.
  • Width is the terminal's scarce resource — the thing a GUI has in surplus and pui does not. Six columns is the whole pane for two fields.

There is one column layout that earns terminal width, and it's Fleet C: put dependency depth on the horizontal axis instead of status. Then left-to-right means something a list physically cannot draw. Keep columns for the DAG, not for the enum.

One clarification on parity, since it's adjacent: D-004's "one source, two renderers" governs the context projection — same data, rendered per surface. It does not oblige the fleet board to be the same shape in both. A GUI has a pointer and unlimited width; pui has keys and 120 columns. Rendering the same data differently is what that decision asks for, not a violation of it.

Part three · sessions

Browsing and switching sessions

Two different problems wearing one name — and the half that holds all the history is currently not reachable from pui at all.

First · what switching costs you today

A flat list you cannot search, missing everything that ended

Today the route is: go to the Fleet tab, find the row, press Enter. resolve_agent_route then does the right thing and tells you in advance which — ⏎ pane · ⏎ window · ⏎ resume · ⏎ menu. That routing is genuinely good and nothing below changes it. The problem is everything that has to happen before it.

Already built (and underused)

  • Four-way Enter routing with the destination shown before the keypress.
  • A typed command palette — parse_palette_command: layouts, crews, theme, pickup-plan-item.
  • Crews and layouts — saved, named, restorable pane sets. Already the right primitive for "put me back in that whole arrangement", and not currently pointed at session switching.
  • Roster grouped by fleet, colour-coded, stable-sorted by heartbeat recency.

Missing

  • Any search. visible_roster() filters on exactly one thing — plan_filter — then sorts. No text match, no state facet, no fleet facet, no recency.
  • Any MRU. No notion of where you just were, so bouncing between two sessions is two full navigations every time.
  • Every ended session. Zero references to sessions:search or sessions:read anywhere in the crate.

"All sessions" currently cannot mean all sessions

The roster is presence-primary: a row exists because a session is heartbeating. An ended session has no presence row, so it is not in the list to be found. Only ones that happen to carry an adv_session_id launch record surface at all, as ⏎ resume.

Scale makes that lopsided. A representative moment from this workspace: 324 agents in scope — 79 live, 100 parked, 543 ended, 35 recorded. So the surface you can browse is an unsearchable flat list of ~179 rows, and the ~578 sessions holding the actual history are invisible — even though every one of their transcripts is indexed and owner-scoped across carry-respawn chains, one sessions:search away. That is the gap worth closing.

Sessions A · the one that pays for itself

A switcher overlay on one keystroke

Switching is muscle memory, not exploration: you want the session you are thinking of, from wherever you are, without navigating. One key opens a fuzzy filter over every session — live, parked, and ended — ranked by recency crossed with match quality. Enter hands off to the existing four-way routing untouched.

 ┌─ switch to… ─────────────────────────────────────────────────────────┐

 ├──────────────────────────────────────────────────────────────────────┤
 │ ● su-f6563  live    task engine · P-001        pui-cockpit    8s  │
 │ ◐ su-b7567  live    task ops user-side · P-010  pui-cockpit   12m  │
 │ ◑ su-9d0a2  parked  drained · awaiting gate    pui-cockpit    4m  │
 │ ○ su-3ae5e  ended   P-020 chat behaviors      own-tui        8h  │

The ended rows are the point. They are matched from the session index, not the roster, and Enter on one routes to resume — the same route the Fleet tab already computes.

What the user gets

  • Zero navigation: the switcher is available from the chat, the fleet board, anywhere.
  • ⇥ alone cycles most-recently-used, which covers the common case of bouncing between two or three sessions without typing at all.
  • Dead sessions become first-class destinations rather than things you remember existing.

How it's wired

  • Live/parked rows: the roster pui already holds, plus the D-008 sessionState swap so the dots mean something.
  • Ended rows: sessions:search, owner-scoped, which needs no new storage.
  • Enter reuses resolve_agent_route verbatim — no new routing logic, and the ⏎ pane/window/resume/menu contract is preserved.
  • MRU is a bounded ring in app state; the palette that parses typed commands already exists to hang it off.

Sessions · recommendation

Switching and browsing are two features, not one

switchingLatency and muscle memory. One keystroke, fuzzy match, MRU on ⇥. An overlay, never a destination — if you have to navigate to it, it has already failed at its job.
browsingRecognition and recall. Facets, a transcript preview, full-text. A destination, because it is exploratory and needs the width.
restoringWhole working contexts, which is crews — already built, currently framed as a layout feature rather than a switching one.

Build Sessions A first, and make it include the dead from day one

The overlay is 3–4 days and removes the most-repeated interaction cost in the app. But the part that actually changes what pui is is the ended-session tier: every transcript is already indexed and owner-scoped, and pui currently references none of it. Today "browse all sessions" can only show you the ~23% that happen to be breathing.

One dependency worth naming: the state dots are only worth rendering once P-024 (the liveness swap) lands — otherwise the switcher inherits the same lie the Fleet tab tells, and now tells it in the one surface you look at most. Sequence it after P-024, and share the merged session model between A and B so the browser is mostly a second renderer over the same list.

Part four · the work

Seeing the work, and putting agents on it

pui has a good plans board, has never heard of goals, and cannot launch a fleet at all. Three surfaces close that.

First · the shape of the gap

One level missing at the top, and the launcher missing at the bottom

The hierarchy is goals → plans → work items. pui covers the middle well and the ends not at all.

Genuinely good already

  • plans_board.rs — master/detail over every plan: status, a "● N working" agent badge, done/total, sorted active→ready→draft→shipped.
  • Its right pane already shows a plan's work items with who holds each one, their claim liveness, and their declared intent — most of what a work-item view needs.
  • The palette can hand a plan item to an agent already running (PickupPlanItem).

Absent

  • Goals — entirely. Zero references to goals anywhere in the crate. The level that says why a plan exists is not modelled.
  • Fleet launching — entirely. Zero hits for launch-on-plan, fleet:create, launch_agent, LaunchSpec. You can launch one session from the Fleet tab; you cannot put a fleet on a plan.
  • Cross-plan work-item search. Items are reachable only by first selecting their plan.

Do not build a work-item list

This workspace currently holds 39,995 work items. Of those: 24 todo, 4 in flight, 49 needing a human, 355 blocked, 3 stuck.

So the set worth looking at is around 0.2% of the rows, and any surface that opens on "all work items" has buried its own answer by design. The useful primitive is not a list, it is a frontier: what is actionable now, what is in flight, what is waiting on you. Everything else is an archive you query, not a list you scroll.

Work C · the one pui cannot do at all

Launch a fleet from the thing you're looking at

Today launching a fleet onto a plan happens by typing tool calls at an agent. It should be L on the plan you are already looking at — and the launcher should tell you the one thing that is easy to get wrong.

The right-hand case is the one worth building for, and it is not hypothetical — it happened during this very session: five members were launched against an executable frontier of four items, and the mismatch only surfaced afterwards as a leader-brief alert. The launcher knows the ready width before it spawns anything; it should say so while the number is still editable.

What the user gets

  • Fleet launching stops being a thing only an agent can do for you.
  • The account / model / carry choices are shown as defaults you can see, instead of defaults you have to know to ask about.
  • Sizing is checked against the DAG before the irreversible action, which is the only moment it is cheap.

How it's wired

  • fleet:launch-on-plan { name, plan, count, agent, model, account, carry, headless } — the whole form is that call's arguments.
  • Ready width and depth come from the same blocked-by topology as the critical-path surface.
  • The spec preview is scheduler:preview_spec_delta, which reports admits/excludes without writing anything.

Across parts two, three and four, one theme

Every gap on this page is the same gap in a different costume: pui shows state and cannot act on it. It renders the roster but cannot bench a member; it renders plans but cannot staff one; it renders live sessions but cannot reach the dead ones; it renders a green dot that is not checking the thing it appears to check.

So the ordering that falls out is not by surface, it is by leverage: fix the liveness field (P-024, a day) because three surfaces render it; then the switcher, because it is the most repeated interaction in the app; then the launcher, because it is the only thing here that pui genuinely cannot do at all; then the leader cockpit and the boards, which are the payoff once the first three make them honest.
