Database audit 9.2-day measurement window 1 fix shipped & verified

What the database is actually spending its time on

A single expression in one plan-index query was consuming 16.2% of all database execution time — recomputing a boolean 16.4 million times by detoasting a column it never returned. It is fixed, measured at 39× faster. Here is that finding, the eight behind it, and what does and doesn't travel into a shipped build.

How this was measured

Everything below rests on pg_stat_statements, which had been accumulating since 2026-08-20 16:39 UTC — a 220-hour window. Across it the instance executed 9,134,843 seconds of query time. Divided by the window, that is 11.5 backends running SQL continuously, day and night, which is the number every percentage here is a share of.

Findings are ranked by measured share of that total, so the numbering is real ordering, not decoration. Every performance claim was confirmed with EXPLAIN (ANALYZE, BUFFERS) against the live database rather than inferred from the query text.

Do index and tuning decisions reach release builds?

Direct answer
Schema & indexes Yes Embedded Postgres applies the same libs/papercusp/libs/db/sql/*.sql files when its own server boots. Anything in a migration ships.
Server tuning No Planner and memory settings do not live in migrations. They are host-scaled at runtime, and this dev box is nothing like a laptop.
Field telemetry No pg_stat_statements is not in the embedded extension set, so none of this is measurable on a user's machine.

So the good half is genuinely good: I checked all 1,003 non-primary-key indexes in the live database against the full migration corpus. Only 2 are real drift in the core harness_shared schema — plugin_configs_plugin_idx and plugin_enables_plugin_idx, both on plugin_slug, both present here and in no migration file. A shipped install would not get them.

The half that doesn't travel is the one that changes query plans

This box runs shared_buffers = 62.9 GB and effective_cache_size = 188.7 GB. A shipped build derives its settings from the host at boot, falling back to roughly 128 MB. That is a ~500× difference in cache assumptions, and the planner chooses different plans on each side of it. An index that looks redundant here — because the whole table is resident in RAM — may be the only thing standing between a user and a table scan.

Separately: random_page_cost is never set anywhere in the repository. Both dev and shipped therefore run PostgreSQL's default of 4.0, a value calibrated for 2000s-era spinning disks. On SSD or NVMe it is normally lowered to about 1.1. At 4.0 the planner systematically overestimates the cost of random I/O and prefers sequential scans — which is worth weighing against the sequential-scan volumes in finding 5 below.

Two smaller notes for completeness. The five *_embedding_mode_idx indexes initially looked like drift but are not — migration 530 creates them through EXECUTE format(), so their names are assembled at runtime and no text search of the migrations can find them. And the remaining 71 name mismatches belong to dbos (18, third-party), the retired zero_0/cvr sync engine (8), papercusp_marketplace (28) and the plugin/auth schemas — none governed by these migrations.

01

A boolean recomputed 16.4 million times by detoasting a column it never returns

Fixed & verified 16.2% of all DB time · 1,475,779 s · 16,449,742 calls

Plan index reads projected content LIKE '…origin: scout…' AS is_blender_origin inline. harness_plans.content averages 10 kB and is TOASTed — 78 MB of TOAST sitting behind a 2.8 MB heap — so evaluating that LIKE forces PostgreSQL to detoast content for every candidate row, on every read, even though content is never in the result set.

This was the single most expensive statement on the instance. Isolating each expression against identical rows shows where the time actually went:

Query variantExecutionBuffers
Baseline — neither expression1.4 ms360
Plus the correlated EXISTS subquery1.3 ms361
Plus content LIKE … only88.0 ms7,609
Both, as shipped93.3 ms7,610
After the fix2.37 ms321

The EXISTS subquery everyone would suspect is free. The LIKE is 98.5% of the cost, and its 7,250 extra buffers are roughly 58 MB of TOAST read per call. The measured 93.3 ms also matches the production mean of 89.7 ms almost exactly, which is what confirms the bench reproduces the real thing. The punchline: only 24 of 1,612 plans actually match the marker.

What shipped

The flag is a pure function of content, so it belongs in the write path. Migration 1024 adds it as a STORED generated column, computed once per plan write instead of 16.4 million times per nine days. The two primary read paths in source.ts now select the column; the two legacy fallbacks still compute it inline on purpose, since that path exists precisely for a database where 1024 has not applied.

Equivalence was verified across all 1,612 rows before and during the migration — 24 true either way, zero mismatches — and a new pin test ties the SQL literal to the TypeScript constant, with four fixture controls proving the test can actually fail. Without that pin, editing the marker in TypeScript would silently leave the stored column computing the old one forever.

02

work_items carries 39 indexes and cannot do a single HOT update

Open · highest remaining 3.5% of all DB time · 318,879 s · 145.6 ms per update

The hot jsonb_set update on work_items takes 145.6 ms to modify a single row. The reason is index maintenance, and the statistics are stark:

MeasureValueReading
Indexes on the table39Every update must maintain all of them
Index bytes vs heap bytes1,887 MB / 1,826 MBIndexes outweigh the table itself
HOT updates131 of 2,569,9410.0% — the optimisation never engages
Dead tuples13.7%Churn the vacuum is chasing

A HOT (heap-only tuple) update lets PostgreSQL modify a row without touching any index, but only when no indexed column changed and the page has free space. At 39 indexes covering status and friends, that condition is essentially never satisfiable — so all 2.57 million updates pay the full write amplification.

Index usage over the window shows real slack: hfc_see_also_gin (4.5 MB) and hfc_audit_pending_idx have zero scans, and several more sit under 500. The GIN index is the notable one — GIN maintenance is among the most expensive write costs in Postgres, and this one has never served a read.

Recommended: drop the two zero-scan indexes (the GIN first) and review the sub-500-scan tier. Then examine whether the jsonb_set path needs to write indexed columns at all — if payload could be updated without touching status, HOT becomes reachable and the write cost largely disappears. I have deliberately not dropped anything: index drops are destructive DDL and a zero-scan index may still serve a monthly job, so that call is yours.

03

An issues query with 18 opaque boolean parameters, permanently pinned at its row cap

Open 2.6% of all DB time · 235,944 s · 2,092 ms per call

The hot engineer_issues read takes two full seconds and returns exactly 500.0 rows on every one of its 112,742 calls — the signature of a LIMIT being hit every single time, never a natural result size. Its WHERE clause ends with eighteen consecutive bare parameters:

The shape
WHERE workspace_id = $1 AND kind = ANY($2) AND state = $3 AND $6 AND $7 AND $8 … AND $23

These are optional filters passed as booleans that are either a real condition or a no-op true. Because the planner sees opaque parameters rather than constants, it cannot use them to select an index or prune rows early, so the query scans broadly and truncates at 500.

Recommended: build the WHERE clause dynamically so only active predicates appear in the SQL. This makes the conditions sargable and lets existing indexes apply. Worth pairing with a check on whether callers actually want a 500-row cap or are silently receiving a truncated answer — a capped result read as a complete one is the failure mode this repo's own guidance warns about.

04

The claim path builds a 57,000-row temp table and takes nine seconds

Open 1.1% of all DB time · 104,330 s · 8,997 ms per call

CREATE TEMP TABLE claim_candidate_snapshot averages 9.0 seconds and materialises 57,142 rows per call across 11,596 calls. Every agent claiming a work item waits on this, which makes it a latency problem felt directly by the fleet as well as a load problem.

Recommended: this deserves its own investigation rather than a guess from the statement text — the question is whether the snapshot genuinely needs all 57k candidate rows materialised, or whether the selection can be pushed into the query that consumes it.

05

A 3.6 GB audit log written 15 million times and read only by scanning it whole

Open 13.5M rows · 39.9 billion tuples read sequentially

route_invocations holds 13.5 million rows in 3.6 GB and carries exactly two indexes: the primary key, and (workspace_id, invoked_at DESC). Over the window it took 14.9 million inserts and served only 2,658 index scans — against 5,676 sequential scans that read 39.9 billion tuples, roughly half the table per scan.

Reads are rare but each is enormous, and the 975 MB index that exists is barely used, so it is being paid for on every insert and almost never repaid.

Correction: an earlier draft of this report said this table had no evident retention. That was wrong. telemetry-retention registers it at 7 days and is enforcing exactly — the oldest row is 7 days old. The 3.6 GB is not neglect, it is ingest rate: 13.5 million rows in seven days is roughly 22 inserts per second, sustained.

Recommended: index for the predicate the rare reads actually use rather than keeping one the workload has shown it does not want — and, for release builds, shorten the window rather than adding a policy that already exists.

06

The optional-predicate pattern is systemic, not local

Open · pattern 4 sites in plans · 18 parameters in issues

Findings 1 and 3 share a root shape: AND (${flag} OR column = ${value}), repeated four times in the plans source and taken to its extreme in the issues read. The intent is a reusable query with optional filters; the effect is a WHERE clause the planner cannot reason about.

It is worth treating as one fix rather than several. A small helper that composes only the active predicates would remove the whole class, and the two query builders are the natural place to put it.

09

Query-safety review: nothing alarming

No action needed 611 .unsafe() sites reviewed

I checked the injection surface across roughly 735 raw SQL call sites and found no confirmed SQL injection. Of 611 .unsafe() uses, none interpolate a template variable into the SQL string. The variable-argument cases pass either pre-built parameterised SQL with a separate params array, or code-controlled identifiers such as column-list constants and table-alias prefixes — I traced a representative sample to confirm rather than assuming.

Two things genuinely worth noting on the positive side: the dev:pg_query tool actively warns when a query against a tenant-scoped table omits its workspace_id predicate, which is a good guardrail against cross-tenant reads; and roughly 66 code sites show a possible query-inside-a-loop shape that would be worth a focused N+1 pass, though I did not verify these individually and some will be legitimate.

Hardening this for release builds

Extend what exists

Almost everything needed here is already built. The retention system works, a tuning-drift checker exists, and migrations already carry schema to the embedded database. The gaps are narrower than they first look — and one of them is structural rather than missing.

The structural one: the tuning check is blind on exactly the target that ships

pg-tuning-drift.ts deliberately skips embedded Postgres, and its stated reason is sound: "an embedded/desktop Postgres is launched by us with -c flags fed from the SAME derivation at every boot, so it cannot accumulate this drift." True — an embedded cluster cannot drift.

But that means it can also never alarm. The check validates "does the live config still match the derivation", when the shipped risk is not drift at all — it is that the derivation itself is wrong or incomplete on hardware we never run. random_page_cost is exactly that failure: not drift, an omission from the derivation, permanent, and with no detector anywhere in the system. Being unable to drift is precisely what makes a bad derivation invisible forever.

Proposal: keep drift-checking native-only, and add a separate derivation sanity check that does run on embedded — asserting the derived values are coherent for the detected host rather than merely unchanged. Is shared_buffers a sane fraction of real RAM? Does random_page_cost match the detected storage class? Does work_mem × max_connections stay inside RAM? Those are answerable at boot on any machine, and they catch the class of fault drift-checking structurally cannot.

The remaining gap is where we measure. Every number in this report comes from one machine with 62.9 GB of cache and a 74 GB database. Users begin at zero rows on a laptop with roughly 128 MB. Neither extreme is where the danger lives — the danger is the middle: a table large enough to genuinely need an index, on a machine where nothing is cached, with random_page_cost = 4.0 actively advising the planner not to use one.

Proposal: add a release-gate check that runs the top statement shapes against a fixture started with the shipped fallback GUCs and small data, asserting plan shape — index scan versus sequential scan — rather than timing. Plan shape is deterministic and CI-safe where wall-clock is not, and it is the property that actually differs between this box and a user's.

Finally, the live-versus-migration index comparison that found the two drifted indexes was hand-rolled for this audit. It is a short query against pg_indexes and the migration corpus, and it answers the exact question you asked — will a fresh install have the schema this box has? That belongs in the gate as a standing guard, not in an audit somebody happens to run.

What I would do next, in order

  • Set random_page_cost to ~1.1 and ship it as part of the host-scaled tuning. It is one line, it affects every query on both dev and user machines, and today the value is an unexamined default calibrated for hardware nobody runs.
  • Take finding 2 (the 39 indexes). It is the largest remaining share of database time and the fix is mostly deletion.
  • Fix the optional-predicate pattern once, covering findings 3 and 6 together rather than one query at a time.
  • Decide retention for the four archive tables — this is a shipping requirement, not housekeeping, because unbounded growth on a user's laptop is a far worse outcome than it is here.
  • Add the two drifted plugin indexes to a migration, so the live database and a fresh install stop disagreeing.
  • Consider shipping pg_stat_statements in the embedded extension set. Without it there is no way to learn what a real user's database is doing, and everything in this report would have been invisible.
