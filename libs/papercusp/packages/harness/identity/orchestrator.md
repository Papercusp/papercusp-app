# IDENTITY — orchestrator

This file is your durable, cross-mission memory. Curator maintains it (append-only). You read it at startup to carry forward lessons from prior missions that the current mission's `.papercusp/memory/summary.md` doesn't capture.

## Patterns I've learned

- [2026-04-26] Read `.papercusp/config.json#phase` and `#itemStates` before doing anything else. If your decision rules reference lifecycle keywords (`todo/validating/passed/failing/blocked`) that do not appear in `itemStates` or in any feature's `status` in `features.json`, you are in the wrong phase — escalate on the first run rather than looping. A coding-harness orchestrator dispatched into a `phase: org` harness has zero valid transitions; every loop re-emits the same escalation and burns hours (run 1777193472 looped ~4h / 6 reviewer cycles before the mismatch was captured).
- [2026-06-02] **Two distinct "feature has 0 commits despite climbing attempts" stalls, both of which NEXT_WORKER cannot fix — escalate instead.** (a) *Poisoned PG chunk plan*: the chunk-loop driver logs "resumes from PG — N chunks, 0 already committed" then immediately re-aborts because the chunk's `files[]` is malformed (contains a directory like `node_modules`, or a typo path) → scratch-sync `copyfile()` EISDIRs BEFORE the worker runs; the worker never reaches its files to fix them, so every re-dispatch re-aborts. The impl is often already complete+staged. Needs a HUMAN to reset PG chunk `files[]` to real paths (or commit the staged work directly). (b) *Empty-chunk-loop / wrong claim pointer*: the worker DOES run but anchors on a claim pointer that doesn't match the real fix site, lands nothing, validator FAILs "no commit ever produced" — needs the scoper to reconcile the pointer. Diagnose by reading run.log for the "0 already committed → abort" signature (→ a) vs `git log --all | grep <id>` empty with a worker that ran (→ b). Evidence: F-FIX-028/F-FIX-030 (a, 3 wasted re-dispatches), F-FIX-024 (b, 7 attempts) — sheets-clone.

## Failures I've seen

- [2026-04-26] Coding-harness `orchestrator` role looped uselessly inside a `phase:org` harness — no feature ever carried `todo/validating/passed/failing`, so `NEXT_WORKER`, `NEXT_VALIDATOR`, `convert_issues`, `next_architect`, `done` were all inapplicable. Each loop re-emitted the same escalation. Run `1777193472-orchestrator`. The signal you have this fault: every transition predicate evaluates false on the first feature you inspect.

## Context shortcuts

- [2026-04-26] Phase → role/lifecycle map: `phase:org` uses roles `coordinator / director / auditor` with lifecycle `proposed → approved → in_progress → launched / paused / cancelled`. Coding-phase uses lifecycle `todo / validating / passed / failing / blocked`. Source of truth: `.papercusp/config.json#phase`, `#itemStates`, `#roles`. Check these before assuming any transition keyword exists.
- [2026-04-28] If the harness-features CLI is absent AND localhost:3001 returns 404 AND features.json is a stub/test file, the feature queue is completely inaccessible. Escalate immediately on the first iteration with reason "feature queue inaccessible" — do NOT retry or loop. This is an infrastructure fault requiring supervisor intervention, not a recoverable condition.
- [2026-04-30] When features.json is lost/stubbed but Postgres/CLI are also inaccessible, supervisor can restore from git: `git restore .papercusp/features.json`. This recovers the last committed feature state (status, attempts). Suggest this to supervisor explicitly in the escalation rather than just asking to 'restore Postgres'. Evidence: sheets-clone 2026-04-30 recovery.
- [2026-06-02] The LIVE operator API is authoritative for status/attempts — on-disk `.papercusp` snapshots (and debugger notes derived from them) can lag the API by a full attempt; when they disagree, trust the API. Two tooling traps that silently corrupt your reads: a `jq` npm shim on PATH may be broken (missing `colors` module) — prefer `/usr/bin/jq`; and the bwrap bash sandbox sometimes breaks entirely (`Can't mkdir /home/node_modules: Permission denied` on every command, even curl/git) — when it does, inspect feature/issue state via Read/Glob/Grep on `.papercusp` rather than the API. Evidence: F-FIX-028 (sheets-clone).
- [2026-06-10] **Gym harness: feature status does NOT auto-transition from `validating` to `passed`.** The director/orchestrator must explicitly update the feature row to `passed` in PG (or via API if registered) after receiving all-PASS validator output, before emitting DONE. If this step is skipped the feature stays `validating` and DONE fires without recording success. Evidence: gymbaseline013f2767a19 F-GYM-99DE522A director raw.md entry.
